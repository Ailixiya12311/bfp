## 1. 当前能力与交付目标

BFP 的握手、会话、流、恢复、调度和记录层由本项目实现。Mihomo/sing-box 负责应用入口、规则、DNS、fake-IP 和操作系统 TUN。原生接入应把它们的 outbound 接到 BFP Session，默认建立 UDP 载体，失败后使用同一认证服务器的 TCP 恢复；业务 TCP/UDP 语义由原来的 BFP 流保持。

| 路径 | 当前状态 | 可作出的结论 |
|---|---|---|
| 应用 → 本机 BFP SOCKS5 → BFP 服务端 | `adapter/socks` 已实现，仓库有 CONNECT、UDP ASSOCIATE、半关闭、来源绑定和清理测试 | 本项目 SOCKS 接入口可运行 |
| Mihomo/sing-box SOCKS outbound → 本机 BFP SOCKS5 | 可作为接入测试路径，尚未对下面选定版本运行真实软件矩阵 | 不能据此宣称某版本 TCP/UDP/TUN/fake-IP 全部兼容 |
| Mihomo 原生 `bfp` outbound | v1.19.32 fork；native-attempt04 测试 8 pass、vet 和两平台 CLI 构建通过 | TUN/DNS/IPv6/route/race/WAN 待验收 |
| sing-box 原生 `bfp` outbound | v1.14.2 fork 14 路径补丁；10 顶层+2 子测试、vet、Windows CLI/check PASS | Linux、TUN/DNS/IPv6/route/race/WAN 与完整矩阵待验收 |
| 上游正式收录 BFP | 没有上游提交或发布证据 | 不属于当前发布支持范围 |

SOCKS5 的域名地址可以保留域名，但只有 IP 的输入不能恢复原域名。SOCKS5 本身没有标准字段携带命中规则标签或进程身份。本机 loopback no-auth 接口只用于受限本地入口。

## 3. 公共适配边界

原生接入使用 BFP 公共适配层，再分别对接两项目。下面的合同仍约束未覆盖的完整支持范围；next22/23 已提供部分公共 PacketConn/metadata API，两个 fork 已有实验实现。

```text
Mihomo ProxyAdapter                     sing-box adapter.Outbound
         │ metadata + context                    │ Socksaddr + context
         └───────────── BFP 公共适配层 ─────────────┘
                         │
             元数据规范化 / classifier / UDP PacketConn
                         │
                 Client.Connect(ctx)
                         │
                 Session.DialClass(ctx, Target)
                         │
               默认 UDP 载体 → 同服务器 TCP 恢复
```

当前可调用的核心 API 为 `session.NewClient`、`Client.Connect`、`Client.Close`、`Session.DialClass`。当前 `protocol.Target` 只有 `Network`、`Address`、`Domain`、`RuleTag`、`Class`；没有 source/process 字段。TCP 流返回 `net.Conn` 并支持 `CloseWrite`。UDP 流也返回 `net.Conn`，但每次 `Write` 是一条报文，每次 `Read` 是一条报文；它不是可直接替代 `net.PacketConn` 的对象。

一个 outbound 实例拥有一个 Client；多个目标流复用该 Client 的 Session。实例 `Close` 关闭 UDP 适配资源并关闭 Client。配置热更新先创建新实例，旧实例保持其现有连接至上游释放，不把不同服务器、不同设备身份或不同准入配置的连接合并到同一 Session。当前 Client 不会在一个已经销毁的 Session 上自动创建全新 Session；原生适配层必须明确更新实例或重建 Client，重建会话后的旧业务连接不能承诺继续存活。

必须开发并测试的公共层能力：

1. 凭证加载和验证。读取私有凭证文件时调用 BFP 内部安全读 API；外部 fork 不能直接 import `bfp/internal/securefile`，应由 BFP 自己的公开适配包封装。示例和日志不写真实私钥、Ticket、恢复秘密或准入值。
2. 生命周期取消、连接半关闭、deadline、资源配额与关闭等待。需要保证 wrappers 不把 `CloseWrite` 丢失成完整 `Close`；Mihomo 的扩展连接包装必须用真实半关闭用例验证。
3. carrier socket 的拨号注入。当前 `ClientConfig` 没有载体 dialer 字段，bootstrap 直接使用 `net.Dialer`。将上游 `interface-name`、`routing-mark`、`bind_interface`、socket protection 或 detour 字段写进配置，当前核心不会自动执行。完整原生实现须增加明确的 TCP/UDP carrier dial hook，再桥接上游物理出站 dialer；没有该 hook 时，仅能把数字 endpoint 和已验证的操作系统路由排除作为受限实验方案。
4. 域名、规则提示和类别输入。class 为 `Interactive=0`、`Normal=1`、`Bulk=2`；类别只影响调度，不改变 TCP/UDP 可靠性，也不能绕过出口策略。
5. 固定目标 UDP 流到 `net.PacketConn` 的映射、回包地址和有界生命周期，详见第 6 节。

| `tunnel/tunnel.go` | 在 TCP/UDP `resolveMetadata` 取得 proxy/rule 后、实际 dial 调用前，将原始域名及稳定规则 ID 放入 BFP 专用 context |
| BFP 公共适配包 | 持有 Client、构造 Target、PacketConn 资源与分类器；不在 Mihomo 中复制协议安全实现 |

TCP 返回值通过现有 `outbound.NewConn(flow, adapter)` 包装；UDP 通过现有 `outbound.NewPacketConn(packetConn, adapter)` 包装。源码中的 `NewConn`/`NewPacketConn` 会追加 chain 并处理 deadline；不能只返回裸 `*session.Flow`，也不能把裸 Flow 冒充 `C.PacketConn`。

### 4.2 域名和规则元数据

该版本 `Metadata` 有 `Host`、`SniffHost`、`DstIP`、`DstPort`、`DNSMode`、进程字段，没有标准的命中规则标签字段。`SpecialRules` 是现有特殊路由输入，不能冒充本次命中规则。

`tunnel` 的 TCP/UDP 路径持有 `rule`，但调用 outbound 时只传 context 和 Metadata。补丁应在规则选定后建立不可变的提示快照，用 BFP 公共适配包定义的 context key 传递。规则 ID 建议由“配置快照 ID + 规则位置或规则集成员标识”构成；展示字符串 `RuleType/Payload` 用于诊断，不作为跨版本稳定身份。全局模式、DIRECT、规则为空、规则重匹配等情况都要有明确空值或最终规则语义。并发流不能读取一个全局“最后命中规则”。

还要在 `Metadata.Pure()` 清除 Host 之前保留原始分类域名。拨号目标仍尊重 upstream 选定的 `DstIP`、hosts 改写和目的端口；有真实域名目的地址时可发送域名 Address 让出口解析。单独 sniff 出的 SNI/Host 只作为 `Target.Domain` 分类提示，不能静默改写目的地址。

### 4.3 carrier 路由

该版本 `BasicOption` 有 `interface-name`、`routing-mark`、`dialer-proxy`，并能构造 `C.Dialer`。这些选项只应应用于连接 BFP 服务器的 carrier；目标业务连接由远端 gateway 建立。第一版原生适配器应拒绝不支持的 detour、UoT 或 mux 组合，避免配置被接受但实际忽略。BFP 自身已有会话复用；额外启用上游 mux 需另行证明不会破坏类别和报文边界。

### 5.2 上下文与地址

通过 `adapter.ContextFrom(ctx)` 读取 `InboundContext`，空上下文必须可用。该版本有 `Destination`、`OriginDestination`、`Domain`、`FakeIP`、`RouteRule`、`RouteOutbound` 和 `ProcessInfo`。TCP/UDP route 路径在选定规则后写入 `RouteRule=selectedRule.String()` 及 `RouteOutbound`；这证明存在提示来源，但 `RouteRule` 是展示字符串，不等同于稳定 rule tag。

适配器复制需要的字段，先使用目的 `M.Socksaddr.Fqdn`，再使用上下文的分类域名。`M.Socksaddr` 支持 IP 和域名；不能把 FQDN 强制塞进 `net.UDPAddr.IP`。需要稳定标签时，根据本地配置快照把 `RouteRule` 规范化到明确映射的 ID，或补充路由上下文；映射缺失时 RuleTag 为空，不猜测规则名。`RouteOutbound` 是路由到的出站标签，也不是规则身份。`ProcessInfo` 只在本地参与允许的分类，不加入当前 OPEN，也不默认发送给服务端。

使用该版本的公共 dialer 构造路径建立 carrier，遵守实际支持的 `bind_interface`、`routing_mark`、域名解析和平台 socket protection。若 dial hook 尚未实现，配置解析必须拒绝无法兑现的选项，支持范围仍是路由排除后的实验模式。

## 6. UDP PacketConn 合同

一个 BFP UDP Flow 在 OPEN 时固定目标，服务端解析/拨号后固定一个数值目标 socket。上游 `net.PacketConn.WriteTo` 可为不同报文提供不同目标，两者不能直接等同。公共适配器按 PacketConn 实例维护“规范化目标 → BFP UDP Flow”的映射，多目标分别 OPEN，不改变已经 OPEN 的流目的。

| 操作 | 必须满足的语义 |
|---|---|
| `WriteTo(payload, addr)` | 校验目的地址和端口，取得目标流；一次 Flow.Write 对应一条报文；空报文可用，超过 16 KiB 返回明确大小错误，不能截断、合并或当字节流分次重试 |
| `ReadFrom(buffer)` | 从有界回包队列取一条报文；返回此报文所属目标的上游逻辑地址，绝不能返回 BFP carrier 服务器地址或内部临时地址 |
| connected UDP `DialContext` | 只允许 dial 时固定目标；用连接形式 Read/Write 保留每条报文边界，不能对陌生目标隐式改路由 |
| 多目标 `ListenPacket` | 在约定范围内接受 numeric addr 或 `M.Socksaddr` 域名地址；地址规范化后按目标建流，目标缓存受 Session 剩余流额度及适配器独立限额共同约束 |
| deadline/cancel/Close | deadline 作用于读写等待；Close 幂等，取消待 OPEN、关闭全部目标流、唤醒等待和收束 worker，不关闭其他 PacketConn 的 Session |
| buffer 太小 | 按选定上游实际 `net.PacketConn` 预期定义截断行为或明确错误；底层 BFP Flow 不支持任意小 buffer，内部先用 16 KiB 缓冲读整条，再转换，须测试，不能无声改变行为 |

候选配额为每 PacketConn 最多 16 个目标流、32 条回包队列，且始终服从 Session 默认 32 个活跃流和可靠/不可靠缓冲限额。缓存空闲回收、超限返回值及上游 UDP timeout 要在补丁中冻结；这些数值不是当前已实现原生适配器的参数。一个 native UDP 适配器不得用自己的默认 16/32 配额推导全进程内存上限。

DNS/packet address 首版应选择明确模式：

- 已由上游解析到真实 IP 的目标：保留 `Target.Domain` 分类提示，用实际 IP:port 建立流，回包恢复 upstream 的逻辑目的。地址键至少包含 IP/域名种类、规范化 host 和端口，IPv4-mapped IPv6 应规范化，IPv6 bracket 正确保留。
- 上游仍传入域名且选择远端解析：OPEN Address 保留 domain:port；本机无法从当前协议获得服务端最终 DNS 选择的 IP，因此 `ReadFrom` 使用请求的域名逻辑地址。Mihomo/sing-box 包装器是否接受这种地址、其 fake-IP/domain NAT 如何还原，必须单独通过实测；通过前不标记 remote-DNS UDP 支持。
- 不能为满足 UDPAddr 类型而在本地再次查询一个可能与服务端不同的 IP，并冒称该 IP 是实际回包源。也不能直接把 fake-IP 发给远端。

UDP→TCP 载体恢复仍在远端发 UDP，保留报文边界，但 TCP 队头阻塞可能增加时延，过期/丢弃仍允许发生。原生集成不能增加“不丢报”或“实时延迟不变”的承诺。

## 7. 分类提示的信任与优先级

本节最初描述的是 r7 历史路径；r8 已将 classification 接入每条 Session 的独立本地 TX，支持可信规则/Hint/cap、滑动窗口、持续活动、迟滞和空闲恢复。OPEN 的 Class/Domain/RuleTag 不成为服务端可信策略来源；服务端使用自己的本地 policy。实际 API 和验证范围见[分类器接线实现 r8](分类器接线实现-r8.md)，CLI 和可信适配器入口仍待实现，见[入口方案](分类器CLI与适配器接入方案.md)。

原生公共层应沿用 r8 的决策顺序：显式受信任的 `ClassHint` → 具有 `DomainTrusted`/`RuleTagTrusted` 来源的元数据规则 → 目标端口/协议基础规则 → 默认类别。同层 Priority 较大者优先，同优先级按配置顺序稳定决策；本地标记通过 `DialMetadata` 传入，不传到 wire。`ClassHint` 不能直接复用 peer 提供的 Target.Class；解密成功不自动使元数据可信。行为统计只按既定策略变更有效类别，不修改目标，也不减少远端权限校验。原生来源映射、更细 Session 类别预算及真实负载验收仍待完成。

`Domain` 和 `RuleTag` 即使在加密 OPEN 内传输，也只是已认证客户端提供的提示，不是域名所有权、应用身份或授权证据。远端仍按真实目标和出口 Policy 检查；客户端声称 Interactive 不获得额外目标访问权限。sniff 和规则字符串只在本地受控规则中转成 class，不从不可信内容生成无限长标签。设置标签长度、域名规范化和允许值限制，避免规则原文泄漏本地路径、用户信息或膨胀 OPEN。

## 8. fake-IP、DNS 与 TUN 回环排除

fake-IP 的分配、映射、DNS TTL/cache、sniff 和回包 NAT 属于上游。BFP 会话临时地址属于协议内部，两者不共用地址池。Mihomo 选定源码 `preHandleMetadata` 会查询 fake-IP 映射，找到时恢复 Host 并清除 fake DstIP，缺记录时返回错误；sing-box 选定源码也先恢复 Destination 为域名，保留 OriginDestination，再在 UDP 返回路径包 NAT。适配器应在这些流程之后运行并保持上游 NAT，不自行维护一套 fake-IP 分配器。

必须排除的路径包括 BFP 服务器所有实际 IPv4/IPv6 endpoint 的 UDP 和 TCP、loopback SOCKS/control、启动服务器域名解析所需的 bootstrap DNS、上游管理 API。只有业务规则中的 DIRECT 还不足以证明操作系统 carrier socket 绕过 TUN；需要路由表/接口绑定/socket protection 的证据。

选定版本存在 Mihomo `tun.route-exclude-address` 和 sing-box TUN `route_exclude_address` 字段，可用服务器数值 IP 的 `/32` 或 `/128` 作为候选排除。字段存在不证明 Windows/Linux/Android 的实际路由都生效。先以固定数字 endpoint 验证，后续域名 endpoint 的 DNS 更新必须先更新排除及物理拨号路径，再采用新 endpoint。排除失败应明确失败，不能自动退为物理直连业务目标。

| 场景 | 必需检查 |
|---|---|
| fake-IP 正常映射 | 远端 OPEN 不出现 fake-IP；域名规则仍命中；TCP/UDP 回包正确还原 |
| 映射丢失/缓存重启 | 明确失败或上游定义的恢复，不能把保留地址当公网目标拨号 |
| hosts/sniff 改写 | 实际 Address 与分类 Domain 可不同且有来源；没有偷偷切换真实目标 |
| IPv6 与双栈 | AAAA、数字 IPv6、bracket、IPv4-mapped、IPv6 fake-IP、服务器 IPv6 `/128` 排除分别验证 |
| DNS 经 BFP | DNS 业务与 carrier bootstrap DNS 分离；bootstrap 不递归依赖尚未建立的 BFP |
| TUN 开关/接口切换 | carrier 不自捕获；UDP/TCP 两条路径和 fallback 都经过正确物理接口 |
| full-tunnel 泄漏与循环 | 捕获接口流量、路由查询和服务端计数，证明业务没有因失败自动绕过 BFP，且 carrier 没有再次进入 outbound |

## 9. 可重复开发与构建

本节是开发时执行的合同；本轮已有真实 fork 的部分构建和本地运行证据，但没有部署，也没有完成该合同要求的全平台矩阵。

1. 创建独立集成工作目录，取得上述 tag 后验证 HEAD 等于 SHA，不跟随 `latest/main/testing`。保留 tag/SHA、来源和上游 license。BFP 使用一份经 manifest 验证的固定源码快照，不引用正在变化的工作区。
2. 分别维护两个最小补丁集：Mihomo 的 parser/type/outbound/context 补丁和 sing-box 的 option/register/outbound 补丁。共享适配器在 BFP 包中维护；上游-specific wrappers 放在各 fork。以补丁 SHA256 和 patch 顺序标识集成版本。
3. 各 fork 增加本地 `bfp@v0.0.0` 依赖及 `replace bfp => ../bfp`，用于未发布模块的实验构建。该 require/replace 只在 fork 中修改，本轮不改 BFP go.mod。正式依赖发布前还要选择稳定模块路径和版本，不将本地 replace 当作可发行依赖。
4. 选择 Go 1.27.0 候选工具链，运行 go mod tidy 后检查 go.mod/go.sum diff、模块图冲突和上游 build tags。不同项目的 `metacubex/sing` 与 `sagernet/sing` 是不同模块，不能拿一个项目的扩展网络类型替代另一个项目。
5. 构建 native CLI，先跑配置检查，再执行低权限本机 TCP/UDP 测试；TUN 测试使用明确平台权限和临时路由，记录前后状态并恢复。没有对应平台证据就保留待验收。
6. 保存上游 SHA、BFP manifest SHA256、patch SHA256、工具链、GOOS/GOARCH、CGO/build tags、依赖锁、二进制 SHA256 和完整结果。一次成功构建不自动覆盖其他架构、build tags 或 GUI 包装器。

开发者可在未来已准备好的 fork 内采用下列检查序列；只有新增代码和 fixture 已到位后才有意义：

```text
# BFP 固定快照
go test ./...
go vet ./...

# Mihomo 固定提交 + 补丁
go test ./adapter/... ./constant/... ./tunnel/...
go vet ./adapter/... ./constant/... ./tunnel/...
go build -o out/mihomo-bfp .
out/mihomo-bfp -t -f fixtures/mihomo-native.yaml

# sing-box 固定提交 + 补丁
go test ./protocol/bfp/... ./adapter/outbound/... ./option/... ./route/...
go vet ./protocol/bfp/... ./adapter/outbound/... ./option/... ./route/...
go build -o out/sing-box-bfp ./cmd/sing-box
out/sing-box-bfp check -c fixtures/sing-box-native.json
```

上面命令描述完整开发顺序；当前真实 fork 的补丁、部分 fixture、native 二进制和结果文件见 `integrations/` 与 `.staging/native-upstream/`，但这些只形成受限本地证据，不是完整矩阵 PASS。Linux 对实际改动包和集成用例仍需运行 `-race`，至少分别测试所选择的最小 tags 和计划发布的完整 tags；Windows 没有可用 cgo race 工具链时，明确记录 race 未执行，不能改写成通过。
