# 动态写入时限与可取消写锁方案

日期：2026-10-07。状态：后续 revision 的实现设计，尚未实施。r7 主源码已冻结，本文件不改变 r7 行为或验收结果。

本文补齐的是 `Flow.Write` 的操作级时限语义：等待写入串行化、等待 actor admission、TCP 等待接收信用期间，`SetWriteDeadline` 和 `SetDeadline` 的改变都应影响待定 Write。它不把一次 Write 的时限扩展为远端送达时限，也不取消已经提交的 UDP 数据报或 TCP 字节。

## 1. r7 已有范围和缺口

`session/flow.go:160-237` 的 r7 UDP 分支在 `writeMu.Lock()` 之后读取 deadline 快照，把固定 deadline context 交给 `s.call`，并在 actor 的提交前再次检查。它已经防止被阻塞 actor 后的超时请求迟到提交。

仍有两个明确缺口：

1. 第二个 writer 等待 `writeMu.Lock()` 的时间不受 write deadline 限制。
2. 已进入 admission 的 context 使用固定 deadline。等待期间把 deadline 提前、延后或清除，不能更新该 context。

TCP Write 同样持有整个调用期间的 writeMu，每个 900 字节 chunk 使用 deadline 快照的 context，信用不足时调用现有 `wait`。现有 `wake` 是容量 1 的提示 channel，不是能唤醒所有 writer 的 deadline 变更广播。

后续方案应保留单 Flow 的写顺序和 actor 的单线程状态管理，不重写 generic `Session.call`，不把完成 admission 的请求返回为 `0+timeout`，也不在 network goroutine 中直接修改 streams、queue、classifier 或 Stats。

## 2. 建议采用的结构

### 2.1 可取消的写入串行化 token

将 Write 独用的 `writeMu` 换成一个容量 1、初始有 token 的 channel，或等价的内部可取消 gate。调用获得 token 后执行当前 Write 全过程，退出时归还；禁止通过关闭该 token channel 表示 Flow 关闭，避免 send-on-closed 和零值循环取得 token。

等待 token 的 select 同时监听：

- token 可用；
- 当前 deadline timer；
- deadline 变更广播；
- Flow closed；
- Session context 与 done。

当前 `Flow.Close` 仅通过 `post` 请求 actor RESET，实际 `f.closed` 由后续 fail 路径关闭。actor 受阻时不能假设 Close 已经即时发布写入取消。若本 revision 要保证 pending Write 被 Flow.Close 立即解除，需增加 Flow 本地 close-request 通知：Close 在排入 RESET 命令之前发布，writer 和 admission commit guard 都监听/核对它。不能提前关闭 writer token channel，也不能从 Close goroutine 直接修改 actor 的 stream/queue。Close 本身的 post 是否仍会等待 commands 空位，是独立的关闭接口边界，应另行测试与说明。

token 与过期 timer 同时就绪时，不能依赖 select 的随机选择给出正确结果。获取 token 后重新检查当前 deadline 和关闭状态；已过期则立即归还 token，返回 timeout，不进入 actor。

多个 writer 可并发等待；不承诺调用进入时间严格 FIFO，继续保证一个 writer 持有 token 时，其 TCP 字节不与另一 writer 交错，一个 UDP 数据报不会与另一数据报的 admission 交错。

### 2.2 deadline 变更广播

在 Flow mutex 下维护当前 write deadline 和一个 generation channel。`SetWriteDeadline` 或 `SetDeadline` 在更新 deadline 时关闭旧 channel 并安装新的 channel，唤醒所有正在等待的 writer。已有的 read/write wake 提示仍保留，不能让 token 等待者消费信用等待者唯一的提示。

writer 在锁内一次取得 `(deadline, changedChannel, closed/readErr)` 快照，释放锁后创建或重置 timer。任何变更广播到达后，重新读取快照并重新计算剩余时间：

- deadline 提前：待定操作使用新的更早时刻；
- deadline 延后：旧 timer 触发时重新核对当前值，不能错误超时；
- deadline 清零：禁用 timer，继续等待信用或 admission；
- 设置为过去：尚未提交的操作尽快返回 timeout。

timer 到达并不自动等于有效 timeout。返回前必须在 Flow mutex 下复核最新 deadline；如果 extension 或 clear 先获得该锁并生效，旧 timer 事件只能触发重算。

这套广播也可以用于 pending Read 的完整语义，但本 revision 应先界定 Write 范围；不能顺手宣称所有 net.Conn Read/Write deadline 都已经兼容。

## 3. admission 应使用专用的取消/提交状态

不建议对每次 deadline 改变都另起 goroutine 调用 `s.call`，再在外层 select 返回。返回 timeout 后 goroutine 仍可能提交，多个重试还可能重复发送。不断创建新 deadline context 也会让旧 timer 继续产生无关取消。

建议为 Write admission 增加一个内部专用 helper。它直接提交带 operation state 的 actor command，并在 caller goroutine 中等待完成、deadline 变更和取消；generic `s.call` 的其他用途保持不变。

operation state 至少区分：

```text
pending -> committing -> finished
pending -> canceled
```

一个 operation 只对应一条 actor command。状态可由 atomic CAS 管理，但 deadline 值的核对与改变必须有同一 Flow mutex 的顺序保证。result 只在完成 channel 关闭后读取，不能靠轮询未同步的 `accepted`、`err` 或 streams。

### 3.1 Caller 的规则

1. 进入 command channel 前已经取得写 token，检查当前 deadline。
2. commands 满时，用可重算 deadline 的 select 等待，不持 Flow mutex。
3. command 入队后保持同一个 operation；收到 deadline-change 后仅更新 timer，不重复排队命令。
4. timer 到达时，在 Flow mutex 下核对当前 deadline，尝试 `pending -> canceled`。CAS 成功才返回 timeout，保证 actor 后续取出命令时不执行业务 mutation。
5. 如 operation 已经 `committing`，等待完成并返回真实结果，不能同时返回超时再让它提交。
6. Flow/Session 取消也遵循同一 pending 取消规则。committing 的有限 mutation 应完成并报告实际接纳字节；必要时下一 TCP chunk 再返回关闭错误。

如果 channel send 与取消同时就绪，closure 可能仍进入 commands channel，但 canceled 状态必须使它成为 no-op。这是“命令曾排队”和“业务曾提交”的区别。

### 3.2 Actor 的规则和线性化点

actor 先在其单线程领域做不突变的预算、Flow 存在性和业务状态预检查。到真正分配消息编号、追加 TCP chunk 或入队 UDP batch 之前：

1. 短暂获得 Flow mutex，核对最新 deadline 和 Flow 关闭状态。
2. 在该 mutex 保护下尝试 `pending -> committing`。caller 的 timer 取消也使用同一 mutex 顺序。
3. 成功 CAS 是 admission 的线性化点。释放 Flow mutex后，完成有限、无阻塞的 actor mutation；deadline setter 此后发生，不回滚该提交。
4. mutation 不允许调用阻塞 `post`、`call`、socket Write、日志 flush、DNS 或 backend dial。UDP batch 预检查和提交必须有明确的全有或全无语义；TCP 一次只提交一个有限 chunk。
5. 写入 result，转 finished，关闭完成 channel。即使 wall-clock 此时已经过 deadline，也返回真实接纳结果。

若 actor 的 budget 预检查失败，不分配 datagram id，不推进分类器计数，不发送 ClassUpdate。其 error 结果同样通过完成 channel 返回；不能出现 ErrLimit 但已有部分 UDP 分片。

已经获准 `committing` 的 closure 不能因为 caller 在等待时关闭 Session 而失去完成通知。这个区间只有当前 actor 在执行有限函数；应通过测试检查退出路径，不能以无限等待掩盖阻塞 mutation。

## 4. UDP 与 TCP 的不同接纳粒度

UDP 一次 Write 是一整个数据报。序列号、所有分片入队和成功字节计数应在同一提交事务中变化。零长度 UDP 仍是一个有效数据报。超时或 ErrLimit 返回 `n=0`，且不留下任何分片或编号消耗。

TCP 可以分块接纳。返回的 `n` 是已经提交的字节总数：前面的 chunk 先提交、后面的 chunk 因 deadline 或关闭失败，允许返回 `n>0` 和错误。不得撤销之前已报告接纳的字节。

TCP 信用不足时，持有写 token，等待信用 wake、deadline changed、Flow/Session 关闭；每次被唤醒后读取新的 deadline 与信用。现有 `wait(deadline, writing)` 的固定参数不够，应增加 Write 专用的动态等待 helper，read 分支可保留到独立 revision。

基于成功接纳字节的自动分类只能统计提交事务内真实 accepted 的量。取消、预算拒绝、超大数据报和 inactive best-effort drop 必须按已定义的分类策略分别处理，不能把 attempted bytes 当作下载行为证据。具体分类接线由 staging 阶段 A 审查。

## 5. 锁序和退出要求

- caller 可以持有写 token 等 actor，但不能持有 Flow mutex 等 actor。
- actor 可以短暂取得 Flow mutex做提交 guard，不能等待写 token；否则形成 caller 等 actor、actor 等 caller 的锁环。
- setter 只修改 Flow 本地 deadline 状态和广播，不能等待 actor、writer 或 carrier。
- timer 处理只在 Flow mutex 内核对和 CAS，释放锁后返回或等待；不能在锁内做 channel 阻塞发送。
- token 归还必须在所有 error、timeout、closed 和正常出口发生一次。测试应检查后续 Write 能继续，避免资源泄漏变成永久锁死。
- 当前 carrier close 的通知和 TCP incoming 背压实现保持不变。不能依赖一个待处理 actor 命令来取消这些等待。
- 截止等待与 Session cancel 同时发生时，错误优先级需定义；无论选择 timeout 还是 closed，都必须保持 `n` 与真实接纳一致，不留下迟到 mutation。

## 6. 后续实现范围

建议局限于 `session/flow.go` 的 Flow 内部字段、newFlow、Write、SetDeadline/SetWriteDeadline、必要的 Close 本地写取消通知，以及 Write 专用 helper，再增加独立回归文件。若需要 Session 的 Write command helper，可放在 `session` 包中但不改变 generic `call`。scheduler 的 batch 接口应复用分类阶段 A 的全有或全无机制，避免同一项目出现两套不同的 UDP admission 保证。

不修改线格式、加密 nonce、Ticket 期限、UDP 优先策略、WAN operation 阈值和自动分类阈值。实现应在后续 staging revision 进行，主目录 r7 保持冻结。

## 7. 必须先建立的失败回归

每个计时测试都以 channel/barrier 确认操作已进入指定阶段，再修改 deadline；定时器允许正常 CI 调度误差，核心断言是提交状态与后续可恢复性。

| 场景 | 预期 |
|---|---|
| 一个 writer 被真实 TCP gate 阻塞，第二个 writer 等 token；设置过期 deadline | 两个尚未提交的操作按新 deadline 结束；第二个不等首个释放 token，不消耗 id/字节 |
| actor 或 commands queue 受阻，pending deadline 从长变短 | 提前结束，释放后 command no-op，target 未收到取消 payload |
| 原 deadline 到达之前延长 pending deadline | 跨过原时刻仍等待，在新的时限内释放 gate 后成功且仅提交一次 |
| 清除 pending deadline，再跨过原时刻 | 不因旧 timer 超时，取消或释放之后正常收敛 |
| 同时多次提前、延后、清零 | 没有重复 command、timer/goroutine 泄漏或 stale timer 误判 |
| deadline setter 与 commit barrier 竞争 | 取消获胜无 mutation；提交获胜返回真实 accepted；任何情况下不得 `0+timeout` 后发送 |
| TCP 首 chunk 提交、随后信用不足时缩短 deadline | 返回先前 accepted 的准确 n 加 timeout；没有额外 chunk 或重复分类计数 |
| pending 时 Flow.Close / Session cancel / carrier close | 返回合理的关闭或 timeout，所有 waiter 可结束，token 不泄漏 |
| 正常并发两个 writer、空 UDP、16 KiB UDP、TCP 多 chunk | 顺序和数据完整，empty Datagram 定义保留 |
| 新一轮 Write 清除 deadline 后正常发送 | 没有上次取消残留、写锁泄漏或迟到 payload 污染 |

另用 race detector 检查 deadline/setter/result 状态共享，重复运行 commit 竞争回归。全量与严格 WAN 在实现通过后另行验收；本设计文档本身不产生 PASS 声明。
