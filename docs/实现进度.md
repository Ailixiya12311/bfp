客户端的公共 API 为 `session.NewClient(ClientConfig)`、`Connect(ctx)`、`DialContext(ctx, network, address)`、`DialClass(ctx, target)`、`DialMetadata(ctx, meta)`、`Session()` 和 `Close()`。Session 也有三类 Dial 入口及 `FlowClassification(ctx, id)`，Flow 可用 `Classification(ctx)` 取副本。服务器为 `session.NewServer(ServerConfig)`、`Addr()`、`Serve(ctx)`、`Snapshot()` 和 `Close()`。分类只影响发送机会，不改变 TCP/UDP 交付语义或目标权限。

`ClientConfig.Classification`/`ServerConfig.Classification` 的 nil 选择 Normal 默认和候选行为参数；非 nil 显式配置独立校验，零值策略是 Interactive 默认且禁用行为。普通 Dial 不创建可信 Hint，显式 DialClass 受本地 cap，DialMetadata 的信任来自本地 API/适配器、不是 wire。服务端按本地策略分类且忽略 legacy CLASS_UPDATE 对本端 TX 的修改。唯一应用计数仅在 TCP chunk/UDP whole batch 接受后增加，Tick 可在空闲/暂停时演变；恢复保留 classifier/origin，查询无 Tick。全部默认值、信任和原子准入边界见[r8 实现说明](分类器接线实现-r8.md)。

r7 的 UDP Write 在取得 `writeMu` 后读取一次 deadline，actor 入口及编号/分片提交前复核；取消赢在提交之前时不消耗编号或留下分片，有限提交赢后返回实际结果。运行中动态重设与锁等待截止尚未实现；inactive UDP 仍可能尽力丢弃并返回完整 API 写入。TCP 完整输入记录/错误等待队列时，Session 取消或 carrier 关闭可直接退出。上述修复、受控回归和范围见[r7 验收](验收记录-v0.1-r7.md)，不能推导所有 Write 都按动态 deadline 返回或长期双向压力不会暂停。

`Client.Connect` 只复用尚未关闭且内部上下文未取消的当前 Session。当前 Session 已终止时，后续 Connect/DialContext 重新执行首次握手，建立新 Session 和凭证；旧流失败，不迁入新网络。Client 本身 Close 后继续调用返回 ErrClosed。Connect 的调用上下文限制本次建连，成功 Session 的生命周期由 Client 内部上下文管理。服务端另有 Go 进程内 `RevokeDevice(publicKey)`，它不是远端管理 CLI。

“短时局域网”当前是两端临时网络上下文：随机会话 ID、两个临时逻辑地址、流编号和出口资源归属于 Session。它不会额外创建虚拟网卡，不实现 ARP、NDP、广播或局域网发现。全局代理的 TUN、DNS 和 fake-IP 由接入端负责。

## 凭据与配置读取边界

`keygen` 为服务端和设备分别生成 X25519 静态密钥对，再生成部署级 32 B 准入秘密；两个配置分别持有各自私钥，客户端固定服务器公钥，服务端保存授权客户端公钥列表。JSON 中 `[]byte` 使用标准 Base64 编码，Base64 是编码，不是加密。

`internal/securefile` 在 Unix 创建 `0700` 目录、`0600` 文件，使用独占创建和 `O_NOFOLLOW`；读取检查实际打开文件的 owner 为当前 effective UID，group/other 权限位为零。Windows 在创建时设置当前用户 SID owner、禁止继承的 DACL 和当前用户 FullControl；导入文件允许 SYSTEM/Administrators，但拒绝其他有效 allow ACE、NULL DACL 和不支持的权限类型。文件不覆盖。当前 Windows 的真实 ACL 回归已通过；symlink 创建测试因本账号权限不足明确跳过，Linux 对应运行验证由隔离回归记录。

配置只读取普通文件，读取前检查权限和已有路径组件中的链接/reparse；最多读 64 KiB + 1 字节，超限拒绝。JSON 拒绝未知字段与尾随值。构造 Client/Server 时核验私钥与公钥一致、固定服务端 key 合法、授权列表有界且不存在重复/非法 key，并复制凭据，调用者后续修改输入缓冲不会改变运行授权。祖先目录检查不是抗恶意并发替换的原子 walk，部署目录仍须可信；root/管理员或当前账号被控制不在此文件保护边界内。详见 `internal/securefile/README.md`。

操作时使用仅当前用户或指定服务账户可访问的目录，按部署环境验证 ACL/权限；不要把完整配置输出到终端日志、复制到公开目录或提交 Git。实验结果仅允许保存不含凭据的统计与摘要。准入秘密泄露意味着入口可被持有者探测，设备授权和恢复秘密仍分别承担后续权限检查。

下面配置用于说明字段，`<...>` 是必须替换的占位内容，不是合法测试密钥。建议使用 keygen 生成真实配置，再只修改监听、服务端地址与目标策略。

服务端示意：

```json
{
  "listen": "127.0.0.1:51880",
  "credentials": {
    "admission": "<BASE64_32_BYTE_ADMISSION>",
    "private": "<BASE64_SERVER_PRIVATE_KEY>",
    "public": "<BASE64_SERVER_PUBLIC_KEY>",
    "allowed_clients": ["<BASE64_CLIENT_PUBLIC_KEY>"]
  },
  "policy": {
    "AllowPrivate": true,
    "AllowedCIDRs": ["127.0.0.0/8"],
    "AllowedPorts": [19180],
    "MaxConcurrent": 4,
    "Timeout": 10000000000
  },
  "max_sessions": 4
}
```

客户端示意：

```json
{
  "server": "127.0.0.1:51880",
  "tcp_server": "127.0.0.1:51880",
  "socks": "127.0.0.1:1080",
  "credentials": {
    "admission": "<BASE64_32_BYTE_ADMISSION>",

```

## CLI 操作

以下命令均以项目根目录为工作目录。服务型命令持续运行，到 Ctrl+C 或 SIGTERM 结束。JSON 日志不包含完整凭据。

### 1. 构建与生成凭据

```powershell
go build -o .\bfp.exe ./cmd/bfp
.\bfp.exe keygen -out .\credentials-local
```

`-out` 默认 `credentials`，目录必须不存在。生成 `server.json` 和 `client.json`；已有目录/文件不会被覆盖。需要 Linux 实验二进制时可以使用 Go 标准交叉编译，输出摘要必须与测试实际上传文件一致；不以构建成功代替远端运行测试。

### 2. 服务端与本机客户端

```powershell
# 服务端终端：默认配置同时使用 127.0.0.1:51880 的 UDP/TCP。
.\bfp.exe server -config .\credentials-local\server.json -stats 1s

# 客户端终端：认证后启动本机 loopback SOCKS5。
.\bfp.exe client -config .\credentials-local\client.json
```

`server` 输出 `listening` 和按 `-stats` 间隔的会话统计。`client` 输出 `socks_listening` 与首次会话状态。服务端实际监听地址由配置的 `listen` 决定；服务器 TCP 和 UDP 使用同一地址/端口。SOCKS 默认只允许 loopback 监听，不能用 no-auth 模式绑定 `0.0.0.0`。

### 3. TCP/UDP echo fixture 与 probe

先将服务端策略收紧到示例中的 `127.0.0.0/8` 和 `19180`，并显式开启 AllowPrivate。在另一个终端启动：

```powershell
.\bfp.exe fixture -listen 127.0.0.1:19180
```

fixture 在同一端口提供 TCP 字节 echo 和 UDP 整报 echo，TCP 每次 accept 输出 `target_open` 累计值。它是有界实验辅助程序，不应作为公共业务服务。

probe 直接使用协议客户端，不经过正在运行的 SOCKS 进程；因此它建立自己的新会话：

```powershell
.\bfp.exe probe -config .\credentials-local\client.json `
  -target 127.0.0.1:19180 -udp-target 127.0.0.1:19180 `
  -count 50 -size 16384 -interval 100ms -duration 60s `
  -result .\probe-normal.result.json
```

每次 TCP 操作发送随机数据并校验 echo 相等；整次 probe 在同一个 TCP 流上操作，记录 echo SHA-256、完成次数、会话前后状态和最大 TCP 操作耗时。UDP 是同一个固定目标 association 上的独立小消息，每条消息校验边界和内容。

当前 probe 的 `pass` 要求 TCP 全部完成且没有整体失败；配置 `-udp-target` 时，同时要求 UDP 全部完成且 `udp_failed == 0`，失败返回非零退出码。WAN runner 也单独核验这些条件。r7 沿用 r6 每条 UDP 请求至多发送一次、在原截止内丢弃无关回包的合同；1s 预算从第一次 Stats 之前的 `udpStarted` 起算，总 probe 截止可缩短，首次超时继续失败，后续成功不覆盖它。回包关联背景见[UDP probe 修复](UDP探针关联回包修复-r6.md)。

r7 progress 新增 `write_attempted`/`write_accepted`、Write/读取阶段时长、固定 `error_phase`，以及前后 Stats 与 exchange 时长。完整 API Write 返回不是队列准入、线上发送或目标执行证明；读取阶段包含关联与时间检查，不是纯 RTT，毫秒值独立取整。失败可分到设置 deadline、写入前、写入、读取前、读取阶段；遥测不输出原始回包或秘密。详见[r7 遥测与实网定位](验收记录-v0.1-r7.md)。

UDP 协议本身仍是尽力交付，实验的全成功验收不构成 UDP 可靠性保证。最大 TCP 操作耗时包含整个写读循环，不等于单独的切换停顿时间；UDP elapsed_ms 是操作边界观察，不是纯 RTT。首次连接/开流失败可能在结果文件写出之前退出，不能把“无结果文件”解释为成功。

| probe 参数 | 默认 | 限制/语义 |
|---|---|---|
| `-config` | 空，须提供 | 客户端 JSON |
| `-target` | 空，须提供 | TCP echo 地址 |
| `-udp-target` | 空 | 为空时不执行 UDP 操作 |
| `-count` | 50 | 1–10000 |
| `-size` | 16384 | 每次 TCP 字节数，0–1 MiB |
| `-interval` | 100 ms | 操作之间等待 |
| `-duration` | 30 s | 实验上下文预算；操作同时有连接读写期限 |
| `-result` | 空 | 可选结果 JSON，不能填凭据文件路径 |

### 4. UDP 黑洞 relay

在新的客户端配置副本中设置 `server` 为 `127.0.0.1:19181`，`tcp_server` 保持 `127.0.0.1:51880`；其余凭据不变。启动 relay：

```powershell
.\bfp.exe relay -listen 127.0.0.1:19181 `
  -target 127.0.0.1:51880 -blackhole-after 8s
```

再运行 probe：

```powershell
.\bfp.exe probe -config .\credentials-local\client-relay.json `
  -target 127.0.0.1:19180 -udp-target 127.0.0.1:19180 `
  -count 100 -size 16384 -interval 100ms -duration 60s `
  -result .\probe-switch.result.json
```

relay 的时间从 **relay 启动** 起计算，不从首次客户端请求开始；需及时启动 probe，使故障发生时已有业务流。超过时间后双向 UDP 都被丢弃，TCP 直连原服务器不受影响。`-blackhole-after 1ns` 用于初始 UDP 黑洞；`0` 表示不主动丢包。relay 是单设备实验工具，不能用它模拟多客户端入口或作为转发生产服务。

切换验收至少比较初末 carrier/generation、`same_session`、原临时地址、TCP 字节一致性，以及 fixture 的 TCP accept 计数；probe 单独的 `pass` 不证明目标 socket 没有重建。

## Mihomo / sing-box 接入

独立客户端启动 SOCKS 后，在接入端建立 SOCKS 出站指向 `127.0.0.1:1080`，将规则或 TUN 流量送到该出站。需要 UDP 时必须让接入端启用 SOCKS UDP 支持。开发源码基线已固定 Mihomo v1.19.32 与 sing-box v1.14.2，见[接入方案与版本边界](接入方案与版本边界.md)；适配器、构建和这两款真实软件的完整支持矩阵尚未完成。具体配置格式与行为需在真实接入验收时确认。

客户端收到 DOMAIN 目标时可以原样发送给出口策略解析；只收到 IP 时不还原域名。SOCKS 不携带 Clash 规则标签或应用身份。服务器端点和本地控制通道需从 TUN 路由中排除，fake-IP 应由接入端正确还原后再发给客户端。

## 默认参数与资源边界

session.Options 的 Go API 默认值：握手 3 s、探测 1 s、连续无认证接收失效 3 s、断线保留 30 s；每 Session 32 条活动流、每方向单流 128 KiB 可靠缓冲、会话 2 MiB 可靠缓冲；密钥更新 30 min 或 512 MiB，先到者触发。Ticket TTL 默认 20 min、提前 TTL/4 刷新、旧 alias 重叠 min(30 s,TTL/4)、最大会话寿命 24 h，三种截止独立。CLI 的 server/client/probe JSON 新增可省略 `options` 对象，其中 `ticket_ttl`、`ticket_refresh_lead`、`ticket_overlap`、`max_session_lifetime` 使用正的 duration 字符串；其余参数仍使用 Go API 默认。详见[生命周期与配置](会话凭证生命周期.md)。

UDP 初始 cwnd 为 12000 B，采用简化的窗口增长/减半、RTT 平滑、200 ms–2 s RTO 和发送 token 节奏限制。它仍是实验拥塞控制器，不等价于完整冻结的 NewReno/ACK ranges/PTO 规范。PACKET_ACK 当前确认单个记录号和 epoch，没有 ACK ranges 与 ACK delay。

网关默认同时处理最多 32 个解析/拨号，默认总期限 10 s；可按 Policy 配置。SOCKS 默认 128 个控制连接、32 个 UDP control、每 control 64 个目标。Session 的多队列、内核 socket、日志和运行时开销不能仅凭可靠缓冲限额推导成草案的“总用户态 8 MiB”。必须结合整体峰值测量。
