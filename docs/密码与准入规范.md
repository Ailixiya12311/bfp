# BFP 密码与准入实现规范

日期：2026-10-07。状态：**当前 Go 实现的实验 v0.1 profile**。

本文记录已经落地的握手、密钥接口、记录保护、首包准入及其边界，供代码核对、回归测试和后续专项评审使用。它不是独立安全审计报告，不构成生产部署安全结论，也不代表 wire 已稳定冻结。完整字段与消息编号见[实验 wire v0.1](wire-v0.1.md)，架构目标见[技术设计草案](协议技术设计-v0.1.md)。

## 1. 身份、准入与恢复相互独立

| 秘密或身份 | 当前用途 | 不能替代的检查 |
|---|---|---|
| 32 B 部署级 `K_admit` | 在昂贵握手之前验证有资格尝试协议入口，并加密 bootstrap | 不能替代设备授权、服务端身份验证或恢复持有者证明 |
| 客户端 X25519 静态密钥对 | 首次 Noise IK 证明客户端设备身份 | 服务器必须检查静态公钥授权列表 |
| 预配置的服务端静态公钥 | 客户端固定出口服务器的密码身份 | 公网 IP、端口或准入密钥不等于服务端密码身份 |
| 32 B `resume_secret` | 对内存中仍存活的 Session 执行 PSK 恢复握手 | 不能仅凭 Ticket、Session ID 或旧报文恢复 |
| 随机内存 Ticket | 定位并约束服务器中的 Session | Ticket 本身不是恢复密钥，不独自授权接管 |

恢复秘密由密码学随机源生成，通过已认证 Noise 响应的加密 payload 交付。它与准入秘密独立。当前 Ticket 是服务器内存中的随机引用，不是可以在另一个服务器实例自行验证并重建连接的无状态票据；重启丢失 Session、Ticket 与出口 socket 后，旧恢复资格不能重新拨号冒充原连接。

部署级准入秘密被一个客户端泄露，会暴露所有使用同一秘密的准入封装及尝试入口；设备静态授权和恢复 PSK 仍须分别验证。当前已实现随机 Ticket 的固定 TTL、逻辑刷新及设备撤销 Go API，绑定首次 IK 身份，并固定 Session 最长寿命，见[会话凭证生命周期](会话凭证生命周期.md)。locator 轮换没有改变 Session 内的恢复 PSK，也不是准入秘密轮换或泄露后安全恢复。每设备准入查找、管理接口与完整运维方案尚未冻结。

## 2. 成熟握手的使用方式

当前依赖为 `github.com/flynn/noise v1.1.0`，基础密码依赖为 `golang.org/x/crypto v0.57.0`。wrapper 选择：

| 阶段 | Noise pattern | 认证与新鲜性边界 |
|---|---|---|
| 首次连接 | `Noise_IK_25519_ChaChaPoly_SHA256` | 客户端固定服务器公钥；服务器在读取首条消息后检查 `PeerStatic()` 是否获授权，再发送响应 |
| 恢复 | `Noise_NNpsk0_25519_ChaChaPoly_SHA256` | PSK 是该 Session 的恢复秘密；每次握手生成新临时密钥，恢复资格及承载绑定由 Session 层检查 |

Noise prologue 为：

```text
bfp/v1/<new|resume>/<udp|tcp>/<attempt_id>/<expected_generation>
```

握手 transcript 绑定模式、承载类型、尝试编号和预期代次。服务端响应携带会话参数、恢复秘密、16 B 新承载句柄及 32 B 新鲜挑战；客户端用新方向记录密钥提交挑战与 `ChannelBinding()`。确认前不接受 `OPEN`、目标 DNS/拨号或业务写入。当前不提供业务 0-RTT。

恢复 pattern 的首条消息可能被原样重放；成功解密它不能独自证明活跃持有者、新源地址回程或承载可提交。服务端仍须验证新挑战、来源绑定、操作代次和原子提交条件。Noise 提供密码握手，流量混淆、准入门、重放预算和 Session 资源所有权另行实现。

## 3. 方向密钥导出接口

握手完成时，wrapper 有意调用库的 **`CipherState.UnsafeKey()`**，复制 Noise Split 返回的两个 32 B 密钥：

- Initiator：Send = split key 1，Receive = split key 2。
- Responder：Send = split key 2，Receive = split key 1。

这是库公开提供但名称明确带 `Unsafe` 的显式密钥导出接口，不能称为已经审计的通用 exporter。wrapper 导出后不再使用原 CipherState 加解密活动记录，也不借用其顺序 nonce 实现 UDP 乱序接收。记录层自行派生用途密钥并管理计数。

握手 hash/`ChannelBinding()` 只用于绑定，不能当保密主密钥。静态私钥、准入秘密、恢复秘密、Split 密钥、握手原文和完整 Ticket 均不应写入日志或公开实验记录。Go 不保证秘密在堆、寄存器或所有复制中完整擦除，本实现没有零化保证。

## 4. 密钥派生及用途分离

所有派生使用 HKDF-SHA256，输出 32 B：

```text
HKDF(secret = secret_or_direction_master,
     salt   = profile_context,
     info   = UTF8("bfp-experimental-v0.1/" + purpose))
```

| 用途 | secret | salt/context | purpose |
|---|---|---|---|
| Bootstrap 长度 | `K_admit` | 当前封装的 32 B 随机 salt | `bootstrap/length` |
| Bootstrap 主体 | `K_admit` | 同一随机 salt | `bootstrap/body` |
| 活动 TCP 长度 | Noise 该方向 master | 当前封装的 32 B 随机 salt | `tcp-frame/length` |
| 活动 TCP 主体 | Noise 该方向 master | 同一随机 salt | `tcp-frame/body` |
| 活动记录主体 | Noise 该方向 master | `handle[16] || epoch:u32` | `record/body` |
| 活动记录头部 | Noise 该方向 master | 同一 handle/epoch context | `record/header` |

整数字节序为大端。用途标签、context 长度和输入顺序必须保持一致；修改会改变实验 wire。恢复 PSK 独立生成，不从公开 transcript 派生。每个新 Carrier 具有新 Noise 方向 master 和随机 handle。

当前 epoch 密钥都从该 Carrier 的方向 master 与 epoch 派生，不是具有秘密擦除保证的单向密钥链；master 泄露可以影响多个 epoch。基于旧秘密的更新不能宣称提供泄露后的安全恢复。

## 5. 首包准入封装

封装结构：

```text
salt[32]
|| ChaCha20Poly1305(length_key, nonce=0,
                   plaintext=body_ciphertext_length:u32, AAD=salt)[20]
|| ChaCha20Poly1305(body_key, nonce=0,
                   plaintext=payload_length:u32 || payload || random_padding,
                   AAD=first_52_bytes)
```

每份封装从密码学随机源抽取新的 256-bit salt。length/body 密钥通过不同用途标签派生，所以 nonce 零值分别在单次用途密钥下使用。安全前提是同用途随机 salt 不重复；当前依赖足够大的随机空间，没有持久化 salt 计数器。

最小整体开销 72 B。Bootstrap 随机 padding 最多 255 B，且不突破调用者的整体上限；padding 位于加密主体内部，不能交付给业务。封装没有明文协议 magic、版本列表、设备 ID 或目标。JSON bootstrap 是解密后的内部格式。

初始请求另使用加密内部JSON的`p`字节字段填充，UDP的Confirm也执行相同策略，TCP的Confirm不增加该内部填充。按当前字段长度，UDP Confirm最小封装为1121 B，外层随机padding仅使用剩余空间，整体上限仍为1200 B。当前READY不使用JSON填充，其53 B加密记录经bootstrap封装后最大464 B；每个UDP Confirm与其重试都须具有足够的输入长度预算，避免独立随机padding使已认证确认无法获得缓存READY。此处填充不改变Noise证明、挑战、nonce或准入密钥派生。

TCP 先读取固定 52 B 前缀并验证长度认证，再检查上限后分配主体。未经认证或已认证但超限的长度不能决定大分配。Bootstrap 库整体输入最多 16384 B，当前 Session 网络实现的 Bootstrap 发送仍限制 1200 B；UDP 数据报不得突破 1200 B。

## 6. 活动记录、nonce 与重放

活动记录：

```text
opaque_handle[16]
|| masked(epoch:u32 || packet_number:u64)[12]
|| ChaCha20Poly1305(body_key,
                   nonce=epoch:u32 || packet_number:u64,
                   plaintext=payload_length:u32 || payload,
                   AAD=handle || unmasked_header)
```

基础开销 48 B。header mask 为：

```text
HMAC-SHA256(header_key, first_16_bytes_of_body_ciphertext)[0:12]
```

掩码 XOR 到 12 B header 上。body/header 密钥用途独立；攻击者修改 handle、header 或 ciphertext 时须通过相应 AEAD 验证。该 HMAC 头保护是自有实验构造，未经过独立密码评审，不能称为标准头保护算法。

发送方向每 epoch 的 PN 从 0 开始，最多发送 `2^32` 条记录。重复发送逻辑帧分配新 PN 并重新加密，不能在同一密钥下重用 nonce 加密不同内容。禁止以已经使用的 key/handle/epoch 重建 sender 并清零 PN；epoch 回绕拒绝。接收方仅尝试当前和一个旧 epoch，未知 epoch 不触发无限派生或查找。

固定反重放窗口为 4096 条记录。只有成功验证 AEAD 和内部长度后才推进窗口，坏包不能推动接收下界。同一 Carrier 的记录去重不替代 Session 的流偏移去重：UDP 晚包、TCP 补传和业务层重试的边界仍由 Session 处理。

## 7. 密钥更新与 TCP Framer

`Open` 不自动派生下一 epoch。接收方处理已认证 `KEY_UPDATE` 后显式调用 `UpdateKey(current+1)`，发送方收到对应确认后开始使用新 epoch；非连续更新和回绕拒绝。

最多保留一个旧接收 epoch；成功接受 4096 条当前 epoch 记录后自动退役，Session 也在接收方向更新后约 5 秒调用 `RetirePrevious()`。旧 epoch 的原重放窗口保留至退役。过度乱序或超过该窗口的旧记录可能丢弃，由可靠流补传处理。

活动 TCP 使用独立 `tcp-frame/length` 与 `tcp-frame/body` 标签的 fresh-salt envelope 包住整个活动记录，结构与 Bootstrap 相同，outer 不增加随机 padding。内层最大 16384 B，外层最大 16456 B；inner RecordCipher 仍承担重放检查。TCP Framer 的任何认证或 IO 失败都会终止该 Framer，不能在损坏位置继续解析。长度保护与二层 AEAD 的计算成本尚需性能评估。

## 8. 主动探测与资源边界

当前应用处理策略：

- UDP 无效准入、未知句柄、坏认证输入静默丢弃。
- TCP 未完成或无效首包在有界期限内无协议应用响应地关闭；内核 SYN/SYN-ACK、开放端口和关闭时序仍可观察。
- UDP 准入通过后登记有界原样封装重放记录，缓存最多 4096 项，约 1 分钟退役。重试使用新封装材料，仍复用同一逻辑操作 ID。
- 未转移 TCP 握手连接最多 64 个，候选握手最多 64 个；昂贵握手尝试具有当前全局 128 次/秒预算。默认握手读取期限 3 秒；候选在约双倍握手期限后清理。
- 所有UDP Bootstrap应答字节不超过对应输入数据报，验证Confirm之后返回READY也维持此限制；客户端以内部填充提供足够预算，不能因准入秘密或通过确认而获得无限响应。
- UDP Confirm 与服务器观察到的候选来源地址/端口关联。当前不支持活动 UDP 来源迁移；地址或端口变化必须建立并验证新 Carrier。
- 恢复状态按Carrier generation绑定，逐项逻辑确认后才发送带快照总数的Done；正常业务发送同时要求对端状态集合完整和本端Done完成确认。同步状态最多4096个，重复激活同Carrier保持幂等，控制记录丢失需重试，不能靠仅收到Done提前开放业务。
- 暂停或恢复尚未完成的Session受原始保留期限约束，默认30秒；反复候选握手、attach、activate或READY不会刷新起点。只有双向同步门槛完成才清除此计时，超时销毁所属连接与资源。

准入验证前的对称密码计算仍会消耗 CPU；当前全局 budget 限制主要状态与昂贵握手，并不是无限规模流量攻击防御。当前没有完整来源级令牌桶、精细错误关闭时序证明或网络边缘防护结论。部署级准入秘密泄露者可以生成合法准入请求，仍需受设备授权、恢复证明及资源预算约束。

临时逻辑地址、流编号、目标、帧类型与业务长度在加密内部。随机 handle 会在一个阶段关联记录，公网 IP、端口、总长度、时序和连接寿命仍可观察。静默失败减少应用层探测信息，不保证端点不可识别，也不保证外观等同 HTTPS。

## 9. 已实施的验证与未冻结事项

密码与封装测试覆盖身份 pin、设备公钥授权、PSK 错误、方向 Split 密钥、transcript 一致性、新握手新密钥、改包、重放、密钥更新与旧 epoch 退役、用途分离、非法 TCP 长度和有界双向 Framer。解析 fuzz 为本地短时实验，不是密码安全证明。

Session 回归补充了源绑定、首接入跨承载幂等、丢 READY 后恢复不重复递增、慢 TCP 首包槽和关闭，以及应用级信用、RESET、迟到拨号结果、恢复完整性和数据报预算约束。这些属于同一实现的测试与代码审查，未通过独立安全审计或跨实现互操作认证。

真实本地UDP/TCP运行测试另外覆盖：业务期间双向epoch推进、旧接收epoch退役后业务继续；有选择地丢弃恢复快照记录时，目标不接收提前开放的业务，重试取得进度后保留原出口连接；反复真实PSK候选握手和激活不能刷新未完成同步的保留期限。测试读取actor状态并在保留期限用例中人工推进维护时间，属于有界本地实验，不等于所有网络环境、独立实现或长期运行验证。

UDP Confirm预算回归使用透明中继直接观察实际新建与恢复握手，检查最小1121 B、实际不超过1200 B以及READY最大464 B；去除JSON填充后的374 B最小请求不足情况也保留为确定性断言。该回归和Runtime回归在单次握手期限配置为1秒时连续10轮通过，完整Session包另连续10轮通过；生产默认HandshakeTimeout保持3秒，调用者context可以进一步收紧期限。此前实际套接字诊断已记录：较大缓存READY会使连续较短合法Confirm被防放大预算抑制。最终修复补足请求预算，未延长测试期限，也未削弱恢复完成前禁止业务的断言；原始失败、诊断和修复后的结果分别保存在r3验证目录并由验收记录关联。

后续正式冻结需完成：准入封装和头保护专项评审、确定性向量、方向密钥导出评估、准入秘密/恢复 PSK 轮换与管理控制面、错误与反重放行为规范、跨实现测试、CPU/内存压力验证、LIGHT 开销及统计特征评估。Ticket TTL、locator 刷新/安装 ACK 和设备撤销已落地，但内部回归不能替代独立安全评审。SHAPED、COVER、FEC、TLS/HTTPS 外观仿真、自动 UDP 回切及跨进程 socket 恢复未在当前密码 profile 中实现。
