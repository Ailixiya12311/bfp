# 分类器接入 Session 方案

日期：2026-10-07。状态：下一轮实现方案，尚未接入 Session。本文在 v0.1-r6 冻结验证期间只读核对当前调用路径，不修改 Go 源码、实验脚本或历史验收结果。下文的接口、类别公告与恢复字段都是待实现合同，不能用本文件证明 r6 已具备这些行为。

## 1. 目标和当前边界

目标是在存活 Session 内，按每个发送方向使用本地可信策略确定基线，再按新接受的唯一业务字节调整调度类别。类别可在 INTERACTIVE、NORMAL、BULK 间经策略调整，可靠字节流、尽力交付数据报、目标授权、流控信用、消息边界和 FIN/RESET 语义保持各自原有合同。

`classification` 已提供规则匹配、可信元数据、最高类别限制、有界时间桶、持续行为识别、冷却和恢复到基线的纯组件。`scheduler` 已实现类别总权重 4:2:1、类别内 flow 等权的分层字节 DRR，并提供 `NewWithLimits`、`DropFlow` 和 `ReclassifyFlow`。这些组件存在不代表 Session 接线已经完成。

当前 Session 仍有以下行为：

| 当前实现 | 需要改变的原因 |
|---|---|
| 每条流只有一个 `effectiveClass` | 本端发送策略与对端发送状态混在一起，两个方向会互相影响 |
| TCP 累计 `sendNext > 1 MiB` 且距上次改类超过 1 秒即降到 BULK | 没有窗口、持续活动、恢复滞后或配置规则 |
| UDP 没有行为分类入口 | 应按成功接受的整报统计，不能按片段重复统计 |
| 收到合法范围的 CLASS_UPDATE 直接改本端 `effectiveClass` | 对端可直接提升本端发送优先级，也会跨方向传播降级 |
| DialContext 内部调用 DialClass 并传入 NORMAL | 接入可信 Hint 后会让默认 NORMAL 提前覆盖配置规则 |
| Session 使用 `scheduler.New` 的会话总字节预算 | 每 flow、每类别、排队条数限制尚未接线 |
| 控制和业务使用相同 flow ID 的 FIFO | 整 flow 重分类会把 OPEN、FIN、信用和 ACK 等控制项一起改类 |

本文按当前源码核对现状。其他进度文档可能保留较早的 scheduler 描述；本次只新增本方案，不改写冻结阶段的其他文件。

## 2. 所有权和安全不变量

以下是不随实现步骤改变的合同：

1. 本端 TX 类别只由本端固定规则基线、最高类别权限和本端行为分类器决定。对端类别公告不直接改变本端 TX。
2. 认证证明消息来自某个设备，不自动证明设备提交的 Domain、RuleTag 或高优先级提示可信。trusted 标记来自本地配置或本地适配入口，不能来自 wire JSON。
3. 每个发送方向独立统计新接受的唯一应用字节。重传、恢复补传、填充、FEC、ACK、信用、恢复快照和协议控制不进入业务计数。
4. 目标和首次 OPEN 身份固定。类别变化不能改写 `target`，重复 OPEN 仍查询同一个操作，不重拨目标。
5. 恢复只能回到本地初始基线，不能凭行为自动升到更高类别，也不能突破本地 `HighestAllowed`。
6. 分类状态由 Session actor 独占。分类时间在 actor 实际处理时采样单调时间，不能使用积压 ticker 的旧时间。
7. UDP 全消息原子接受后才计数一次。失败不能留下该批部分片段，不能通过删除整 flow 回滚该批。
8. 业务类别不替代目标 ACL、接收信用、内存预算、pacing 或拥塞预算。
9. 类别版本按 flow 和发送方向单调增加，跨承载保留，不能回绕。重复或乱序状态不得回退。
10. 同 flow 的控制和业务尚未分离时，不对整个混合队列调用 `ReclassifyFlow`。

## 3. 当前调用路径

以下源码位置作为导航；后续实现改变行号时，应按函数与提交点核对。

| 路径 | 当前源码与行为 | 建议接线 |
|---|---|---|
| Client 创建 Session | `session/client.go` 的 `Connect` 调用 `newSession` | 注入 Client 构造时编译的本地 classifier |
| Server 创建 Session | `session/server.go` 的准入提交路径调用 `newSession` | 注入 Server 构造时编译的本地 classifier |
| 普通拨号 | `session/session.go` 的 `DialContext → DialClass` | 拆为无 Hint 的普通入口，共用私有拨号实现 |
| 显式类别拨号 | `session/session.go` 的 `DialClass` | 显式 Class 转为受本地 cap 限制的本地可信 Hint |
| 收到 OPEN | `session/session.go` 的 `handleOpen` | 固定 wire target，使用服务器本地策略创建本端 TX classifier |
| TCP 写入 | `session/flow.go` 的 `Flow.Write` | 在 chunks、sendNext、TXBuffered 和 accepted 提交后 Observe accepted |
| UDP 写入 | `session/flow.go` 的 `Flow.Write` UDP 分支 | 整消息预检和原子提交成功后 Observe 一次 len(payload) |
| 服务器反方向数据 | `session/flow.go` 的 `bridge`：目标 conn.Read → flow.Write | 沿用 Flow.Write 的本端 TX 入口，不在 bridge 再计数 |
| 业务排队与重传 | `session/session.go` 的 `maintain`、`classFor`、`enqueue` | 从本端 txClass 取业务类别，不计新的业务字节 |
| 类别接收 | `session/session.go` 的 CLASS_UPDATE 分支 | 停止修改本端类别；新能力中只更新 peer TX 公告视图 |
| 恢复 | `attach` 清空当前承载 queue，`activate` 生成 flowSnapshot | 保留 classifier 和类别版本，新快照只同步发送方公告 |

### 3.1 TCP 的唯一接受点

`Flow.Write` 以不超过 900 字节的 part 进入 owner。只有通过流信用、Session 信用、单流保留缓冲和 Session 保留缓冲检查后，才追加 `st.chunks`，增加 `st.sendNext`、`s.totalSent`、`TXBuffered`，并设置 `accepted = len(part)`。

分类计数放在这次提交之后，每个 part 只观察一次。等待信用而 accepted 为零的循环不计数。一次公开 Write 部分成功后超时，分类总量等于已成功提交的部分，不等于输入切片总长。`maintain` 给同一 chunk 重排队、UDP 记录丢失重发、恢复重新发送同一偏移都不调用 Observe。

服务器从目标读到的数据通过 `flow.Write` 进入同样的接受点。因此客户端的 classifier 统计上行，服务器的 classifier 统计下行；不要在目标 Read、目标 Write、Flow.Read 或接收重组处再次观察相同业务。

### 3.2 UDP 的整消息接受点

当前 UDP Write 超过 16 KiB 拒绝；inactive 或恢复未完成时可能记录丢弃并返回 `len(b), nil`。因此不能根据公开 Write 返回值判断分类是否接受了业务。该分支内部需要显式区分 accepted 与 dropped。

成功批量提交整消息的所有片段后，调用一次 `Observe(elapsed, uint64(len(payload)))`。零长度数据报仍提交一条带边界的消息，但业务字节贡献为零。超限、容量失败、离线丢弃、消息编号耗尽均不计数。

### 3.3 服务器下行元数据

服务器反方向业务使用这条流固定的目标和服务器自己的规则。network 和目标服务端口来自 OPEN 的固定目标，实际 numeric peer 可由 Backend 已建立的连接提供绑定事实。目标连接的服务器本地临时端口不能作为业务目标端口。

远端提交的 Domain、RuleTag 和 Class 默认为不可信提示。不能对 numeric peer 做 PTR 查询后伪造一个可信原域名，也不能从端口推测 Clash 标签。只有服务器本地可信来源明确提供元数据时，才设置相应 trusted 标记。Backend 的 numeric peer 不自动提供原始应用域名、Clash 命中规则或应用身份。

## 4. 本地配置与拨号 API

拟增加的公开配置字段如下，属于方案示意，并非当前已实现 API：

```go
type ClientConfig struct {
    // existing fields ...
    Classification *classification.Config
}

type ServerConfig struct {
    // existing fields ...
    Classification *classification.Config
}
```

`nil` 明确选择 `classification.DefaultConfig()`，默认 NORMAL 并启用其候选行为参数。非 nil 配置按显式值验证；`Config{}` 与 DefaultConfig 不同，不能偷偷改写其零值含义。禁用行为修正使用显式 `Behavior.Enabled=false`，规则和 cap 仍有效。

NewClient/NewServer 在主要连接或监听资源分配前调用 `classification.New`。编译后的 classifier 不可变，可由多个 Session 共享；每条流的行为 Flow 仍由各自 actor 独占。运行实例不得再次读取调用者原始配置指针或可变规则切片。

Session 保留 DialContext/DialClass，并增加 DialMetadata。Client 如需直接供原生 adapter 使用，可增加同名的 Connect 后转发包装，不能重新引入普通入口的隐式 Hint。

| API | 初始元数据和 Hint |
|---|---|
| `DialContext(ctx, network, address)` | 无 ClassHint；不生成 RuleTag；原样保留真实提供的目标地址 |
| `DialClass(ctx, target)` | target.Class 转为 Trusted=true 的本地 ClassHint，受 cap 限制；不默认 Locked |
| `DialMetadata(ctx, meta classification.Metadata)` | 由本地可信 adapter 明确提供 DomainTrusted、RuleTagTrusted 和 ClassHint 来源 |

三个入口共用私有 `dialMetadata`，只在该路径创建固定 OPEN target、分类基线、行为状态和流操作。验证失败发生在流编号分配和 OPEN 提交之前。Hint 值应复制，调用者之后改变原指针不能改变运行状态。

DialClass 中 Domain/RuleTag 不因“这是本地函数调用”自动获得 trusted 标记。普通 DialContext 不经 DialClass，否则构造的 NORMAL 会成为 trusted hint，提前覆盖配置中的 network、端口和元数据规则。

元数据规则的优先级采用现有纯组件合同：可信显式 Hint → 依赖可信 Domain/RuleTag 的规则 → network/port 规则 → 默认；同层 Priority 降序，同优先级保持配置顺序。所有结果先受 HighestAllowed 限制，Locked 阻止行为调整。

### 4.1 SOCKS 和原生接入的来源边界

SOCKS 确实提供 hostname 时，可以明确记录“请求实际提供的目标名字”，经规范化后由 adapter 调用元数据入口。只有 IP 的请求不反推名字。fake-IP 的还原由接入端完成，不能将 fake-IP 或猜测结果当作可信域名。

SOCKS 本身没有 Clash 命中规则标签或应用身份。本轮不为它生成 RuleTag。Mihomo/sing-box 原生 adapter 只有实际 API 提供了这些字段时才传递，并保留各字段来源；不会因为配置里出现某个规则名称就声称取得了该连接命中的规则。

trusted 在这里表示本地分类政策接受该来源，不表示域名或标签可替代身份认证和目标授权。当前纯组件只接受 ASCII DNS 名字；确实有国际化域名时由本地接入端按明确的 IDNA 规则转换，不做猜测。

## 5. Session 内部 TX 状态

建议拆分当前 effectiveClass，示意字段如下：

```go
type streamState struct {
    target protocol.Target // immutable first OPEN metadata

    txClassifier *classification.Flow
    txClass      protocol.Class
    txVersion    uint64
    txAcked      uint64
    lastClassSend time.Time

    peerTxClass   protocol.Class
    peerTxVersion uint64
    peerTxKnown   bool
    // existing reliability and target state ...
}
```

每端一个本端 TX classifier 已足以表达双向行为独立：客户端 TX 是客户端到服务器，服务器 TX 是目标到客户端。peerTx 字段只是对端发送状态公告，不修改 txClassifier、txClass、目标 ACL 或流信用。初始 baseline 只创建一次；目标不变的恢复不重新套用配置或创建新的 classifier。

Session 对外读取分类状态时通过 actor 获取快照。建议快照分开显示 `LocalTX` 与 `PeerTXAnnounced`，不能将对端未确认或未知的公告写成已验证的本地调度状态。不要向调用方暴露可并发写入的 classification.Flow 指针。

## 6. actor 内分类时间

Session 创建时保存包含 monotonic 部分的分类原点。每次 owner 处理 Write、Tick 或类别观察时，从实际处理时刻计算 `time.Since(classificationOrigin)`；同一 owner 轮次可共享一次新采样。

`maintain(now)` 的 now 来自 ticker channel。积压 ticker 的时间可能早于刚处理的 Write，不能直接把它作为分类 elapsed。分类时钟与握手新鲜性、Ticket 期限、网络 RTT 等时钟职责分开，测试注入也只影响分类时间。

Tick 至少需要覆盖空闲流，才能完成低速恢复。可按分类 bucket 或独立维护节拍触发，避免为已保留的终止流每 10 ms 扫描全部桶。存活 Session 的 classifier 在 suspend/attach 中保留；重试、恢复快照和重新排队不增加业务计数。

accepted 指标衡量应用被 Session 接受的速率，并非实际线上吞吐。承载受阻造成 accepted 减少，可以按所选指标进入低速恢复；不要把这种结果表述为已识别实际网络流速。是否在暂停期间继续 Tick 应在实现合同中固定；本方案选择保持单调时间并继续维护存活的分类状态。

## 7. UDP 原子 admission

现有总字节预检不足以保证新增 per-flow/per-class/items 限制下的批量成功。建议增加 owner-confined 的批量队列预检和提交接口，或一次性 reservation。这里只给出需求，不修改 r6 scheduler API。

原子批次至少执行以下顺序：

1. 校验大小、流状态、承载可接受状态和消息编号是否还有空间。
2. 生成有界片段列表，计算每片完整编码/记录/填充成本及总条数；上限仍为 16 KiB 整报。
3. 同时校验会话、flow、类别的字节和条数预算以及新 flow 数限制，全部通过后提交整个批次。
4. 提交成功才消耗消息编号并增加接受统计，再 Observe 整报业务字节一次。

失败保持队列、消息编号和分类状态不变。禁止失败后 DropFlow，因为它会删除此前已接受的消息、可靠数据或控制状态。编号达到上限时禁止回绕，也不能在回绕后继续建立消息状态。

消息计数成功不意味着已送达目标；它只表示已被 Session 接受。之后 TTL 或切换导致尽力交付消息丢弃，不反向扣除已经发生的接受计数。

## 8. 调度生效范围和控制边界

最小接线选择向后生效：txClass 改变后，新业务排队与后续可靠数据重排队使用新类别；已经排队的项保留原类别和 FIFO。Queue 当前由 head item 的 class 选择外层类别，因此一段旧类别队列仍可暂时位于新类别项之前。该延续有资源上限，但不是立即重分类全部 backlog 的保证。

当前控制与 DATA 共享 flow FIFO，不能对它们整体调用 ReclassifyFlow，否则会把 OPEN、FIN、StreamAck、信用或类别公告一起改为 BULK。若未来要求立即调整所有已排队 DATA，先实现独立控制队列或 data-only 重分类接口，再进行整体应用。

重传路径也要按 frame kind 选择调度类别：StreamData/Datagram 使用本端 TX 类别；控制项保持控制政策，不能因为其 Flow 字段存在而被 classFor 误降。独立控制预算需要有限 burst、速率和队列上限，允许在没有 DATA 出队时推进恢复与密钥操作。所有实际控制字节仍进入 pacing/拥塞预算，不能无限旁路。

Session 创建与 attach 重建 queue 时应使用相同限制配置。backlog 限制与可靠发送保留缓冲是不同预算，不能把 Pop 释放的排队字节当作业务已被确认。

## 9. 版本化发送方公告

当前 CLASS_UPDATE 无版本且改接收方本端类别，不适合直接复用。拟定的新合同是发送方公告：公告方描述自己的 TX 类别，接收方只保存 peer TX 视图。

必须通过认证能力协商或下一 wire 版本选择新语义，绑定认证 transcript。不能把新版公告发送给仍将其解释为“改本端 effectiveClass”的旧实现。当前 r6 的协议语义不因本文改变。

建议冻结字段如下，数值是下一版候选合同：

| 字段 | 公告 | 确认 |
|---|---|---|
| Kind | ClassUpdate | ClassUpdate |
| Flags | 0 | 1 |
| Flow | 已存在的 flow ID | 同一 flow ID |
| Offset | 发送方向的单调版本 | 所确认的本端发送版本 |
| Value | class，完整 u64 校验后转换 | 所确认的相同 class |
| Data | 空 | 空 |

版本从 1 开始。首次有效公告在 OPEN 已成功建立、对端已拥有流状态后提交；现有 OPEN.Class 仍是 legacy 元数据请求，默认不等同已版本化的发送公告。每次实际 TX 类别变化递增一次，不因重发或换承载递增。sender 可只保存最新待确认状态，允许合并版本跳跃。

版本达到上限时不回绕；本方案建议终止该流并保留终止记录，避免复用类别版本或 flow ID。未知/终止 flow 的公告不分配状态、不复活目标。

接收规则如下：

| 输入 | 结果 |
|---|---|
| 合法新版本 | 更新 peerTxClass/peerTxVersion，确认该状态 |
| 相同版本、相同类别 | 幂等确认，可限速合并 |
| 相同版本、不同类别 | 状态冲突，按协议错误拒绝；最小实现可关闭 Session |
| 旧版本 | 不回退，可确认当前最新状态以帮助对端收敛 |
| 版本跳跃 | 允许，仅保留最新状态 |
| 版本 0、非法 Flags、非空 Data、class 超出范围 | 按明确的协议错误策略处理，不修改状态 |
| ACK | 只确认本端已发送的精确 pending 版本与类别；旧 ACK 不确认新状态 |
| 超过本端已发送版本的 ACK | 不接受，不把它变成类别更新 |

peer 公告即使声称 INTERACTIVE，也不改变接收方的本端 TX、规则基线或 HighestAllowed。对端声称的类别不是本地授权证据。正常公告不再诱发反方向的类别修改与公告链。

UDP 公告与 ACK 使用有界逻辑状态重试，TCP 稳定承载按记录流发送，换承载后重建最新状态。普通 PACKET_ACK 不能独自承担跨承载逻辑状态同步。类别公告、确认和重试都进入有限控制预算；它们自身不进入业务字节计数。

## 10. 恢复快照

在采用新能力的 flowSnapshot 中增加发送方自己的 TxClass 和 TxVersion。接收快照只按第 9 节规则更新 peerTx 公告视图，不能覆盖自己的 classifier、txClass、baseline 或业务累计量。

attach 保留各 flow 的 classifier、txVersion、txAcked 和 peerTxVersion。新承载清空旧排队状态后，可靠业务按本端当前 txClass 重排队；分类 Observe 不再次运行。恢复快照只描述已有状态，不重新创建本地可信 Hint，也不把 wire 元数据变成可信来源。

同版相同快照幂等，旧版不回退，同版不同 class 拒绝。恢复同步完成后，尚未确认的最新本端公告继续有界重试。跨 generation 的旧记录已由承载校验拒绝；同一有效承载中的乱序新记录仍要靠类别版本防止回退。

本端发送调度不等待 peer 公告确认。因此公告丢失暂时影响 peer 视图收敛，不阻止业务发送，不改变业务确认与流信用。

## 11. 最小分阶段实施

### A：本地分类器接线与安全计数

1. 构造时编译两端配置，注入 Session，增加本端 TX 状态和 actor 分类原点。
2. 拆分普通 DialContext 与显式 DialClass，增加明确的本地元数据入口；服务器不直接信任 OPEN.Class/Domain/RuleTag。
3. TCP 接入唯一 accepted 点；UDP 先完成原子 admission，再接整报计数。
4. maintain 接 Tick，业务排队和重传读取 txClass，恢复保留原状态；暂时向后生效，不整体重分类混合控制队列。
5. 新 Session 逻辑停止让 legacy CLASS_UPDATE 修改本端 TX。未协商新能力时不发送新版公告，不把 Offset=0 的旧更新写入新版本状态机。

阶段 A 的交付只承诺本地规则和行为分类，不承诺版本化跨端公告已完成。两端可能采用不同本地政策，不要求上下行类别一致。远端 legacy 更新可记录为不受信任的兼容输入，但不得绕过本地 cap。兼容行为需要单独测试和明确发布范围。

### B：版本化公告与恢复收敛

1. 冻结并实现认证能力或 wire 版本门槛，拒绝新旧语义混用。
2. 增加每 flow、每发送方向的类别版本、精确 ACK 和最新状态合并/重试。
3. 首次有效公告、变更公告与恢复快照统一使用 peer-view 处理函数，遵守同版冲突与旧版不回退规则。
4. 接入有限控制预算并增加公告/恢复观测，不能用无限重发达到“可靠”。

阶段 B 才承诺对端 TX 公告最终收敛。它仍不赋予对端修改本端调度的权限。

### C：队列策略的独立完善

将 per-flow/per-class/items cap 在初建和 attach 路径一致接入，完善控制与业务队列的区分。只有此后需要且验证了 FIFO、控制推进和资源上限，才启用 backlog 的即时 data-only 重分类。此阶段不以流量吞吐测试代替状态和资源不变量。

## 12. 运行时测试及不变量

以下测试使用真实 Client/Server、认证承载和目标 socket，覆盖 Session 接线。纯 classification 和 scheduler 已有测试继续运行，不重复编写只镜像纯组件的测试。

| 测试场景 | 必须观察的不变量 |
|---|---|
| 普通 DialContext 命中 network/port 规则 | 默认入口没有隐式 NORMAL Hint 覆盖规则 |
| 显式 DialClass 请求 INTERACTIVE，本地 cap 为 NORMAL | 实际 LocalTX 不超过本地权限；公开输入和 wire 请求不能绕过 cap |
| 可信元数据入口、普通 SOCKS 域名请求、只有 IP 的请求 | 分别保留真实来源；无域名/标签时不会造可信字段；认证 peer 元数据不自动 trusted |
| 小上行请求、持续大下行响应 | 服务器 TX 降到 BULK，客户端 TX 保持基线；目标拨号仍一次 |
| 大上行、小下行响应 | 只有客户端 TX 降级；bridge 不重复计数，方向不串扰 |
| 信用阻塞、部分 Write 超时、信用增加后续写 | 累计 classifier 字节等于真实 accepted 总量；等待与未接受字节不计数 |
| UDP 多片成功、容量失败、离线丢弃、零长度消息 | 成功整报只计一次；失败不留半批、不消耗编号；丢弃不计数；空消息边界保持 |
| UDP 丢包、重传、填充、密钥更新 | 新业务计数不变，控制和冗余不进入行为窗口 |
| UDP→TCP 恢复期间未确认数据补传 | 原 Session/目标/classifier/baseline/version 保留，补传不增加累计量，数据与 FIN 正确 |
| 经真实加密承载发送高优先级公告 | 只修改 PeerTXAnnounced，不修改接收方 LocalTX、ACL、信用和 target |
| 先新版本后旧版本、重复版本、同版不同类别 | 乱序不回退、重复幂等、冲突拒绝 |
| 旧 ACK、未来 ACK、缺失 ACK 和最新版本重试 | 旧/未来 ACK 不确认新的 pending；状态重试有界并最终收敛 |
| 同版与旧版恢复快照 | 只更新 peer 视图，不重置本地分类或重复计数 |
| 类别变化时关闭、RESET 或完成双向 FIN | flow 不复活，不重拨，不继续分配类别状态 |
| idle Tick 恢复 | owner 实际维护路径触发恢复，仅回固定基线，不能超越 cap |
| 持续 DATA 同时有信用、FIN、类别控制 | DATA 改类不把控制误降；控制有限且可推进关闭/恢复 |
| 新旧能力组合与能力降级 | 未协商不发送/解释新版公告，认证协商不能被未认证降级 |

分类持续时间测试可引入 package-private 分类时钟，网络、加密和目标 I/O 仍真实执行。推进时钟通过 owner 或原子受控值完成，不能从测试协程直接修改 classifier。测试只替换分类时钟，不替换认证期限、Ticket 期限和网络 RTT。保留一个短真实时钟 idle 测试，确认 ticker 确实调用分类维护。

测试通过 actor 读取 LocalTX 与 PeerTXAnnounced 快照，并观察目标连接计数、实际接受字节、消息边界、carrier generation、类别版本和缓冲上限。不要用噪声较大的端到端带宽比例作为这批接线测试的唯一判定；类别总份额已有 scheduler 测试，运行时重点证明状态流向和策略权限正确。
