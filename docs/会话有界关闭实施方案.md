# 会话有界关闭实施方案

日期：2026-10-09。适用范围：独立 BFP Go 实现，当前实验 wireVersion 3。

**状态：待实现方案，不是 next9 已完成功能或验收报告。** 本文根据 `.staging/r9-next9` 由 next8 冻结源码复制后的关闭、传输、凭证和 DNS 路径审查编写。审查没有运行测试或远程业务实验。当前轮先完成双协议监听夹具与实际 DNS 终态矩阵；有界关闭在下一轮独立源码边界内实现和验证，不能把一个局部关闭修补记为整项通过。

## 1. 需求与现状

短时会话网络要求会话结束后销毁临时身份、流、出口映射、目标连接和会话 DNS 缓存。关闭通知、确认丢失或承载拥塞不能让已经作出终止决定的一端继续拨号、恢复或重新填充缓存。仍未知道对端关闭意图的一端需要明确的原有故障收束边界，不能承诺任意黑洞下立即远端销毁。

当前源码的事实如下。下表行号指本次审查的 next9 副本，后续实现改变行号后必须重新绑定，不能以此代替实现后的证据。

现有本地 DNS 无故障联动成功只证明通知成功到达时的资源清理。它不证明关闭重传、ACK 丢失、关闭时预算饱和或完全黑洞收束。

## 2. wire3 帧合同与版本边界

现有帧编号足够表达一次不可逆 Session 关闭：19 为 SessionClose，20 为 SessionCloseAck。两者现有发送方都发出全零语义字段，没有理由为了重试额外增加 nonce、关闭序列号或恢复 generation 字段。

下一轮应显式冻结以下 canonical 合同，并同步更新 wire 文档：

| 字段 | SessionClose | SessionCloseAck |
|---|---|---|
| Kind | 19 | 20 |
| Flags | 0 | 0 |
| Flow | 0 | 0 |
| Offset | 0 | 0 |
| Value | 0 | 0 |
| Data | 空 | 空 |

方向由现有认证 record／carrier 上下文确定。一个 Session 只允许一项逻辑关闭决议，关闭后不能再次开启；关闭 operation 的身份就是该 Session 的唯一 Close。每次重试重新 Seal，使用新的 record number，不复用 ciphertext，不降低 replay 校验。ACK 只能确认同一 Session 当前已绑定 carrier 上、本端已经成功完整写出的 Close；PacketAck、Pong、TCP write 成功、旧 carrier 的 ACK 均不能替代。

**这套合同不要求 wireVersion 从 3 增加。** 它保留编号、帧格式和已有合法零字段语义，新增的是内部终态、逻辑重试和本地资源收束规则。现有 wire 文档中 19/20 仅写“会话结束”，并未完整定义关闭状态机，所以必须先将这些规则明确记录，不能以“wire 不变”为由静默引入未说明的协议规则。

旧构建会在发送一次 ACK 后退出；与新构建相遇时，一份丢失 ACK 仍可能导致新端关闭结果为未确认，即使旧端资源已经销毁。因此不能宣称旧／新构建有同等故障恢复保证。若以后增加关闭 token、ACK-of-ACK、跨关闭态的新 carrier、关闭拒绝／错误 payload 或新的必须能力，则需要另行评估显式 capability 或 wire 版本变更。

全零以外的 Close/Ack 不获得关闭成功确认。建议按现有认证协议错误策略立即本地 abort；至少不得将畸形 ACK 当作正常远端完成。无认证输入继续静默，不创建回应状态。

## 3. 不可逆业务终态与有限控制存活

建议采用 `OPEN → CLOSING → STOPPED` 的内部生命周期。CLOSING 只表示有限关闭控制仍可运行，业务资源和恢复资格已经终止。它不是 SUSPENDED，也不能转回 OPEN。

由 `Close()` 调用、本端收到合法 Close、撤销、最大寿命或既有保留期终止作出业务终态决定。首个决定发布一次原子终态标记，并固定起点与 deadline；后续 Close 调用、重复 Close、迟到 ACK、任何普通控制帧、候选握手或 carrier 错误均不能清除此标记或重新计时。

关闭意图的原子发布不能排在普通 commands 队列之后。否则 actor 正在写 socket 或队列已满时，新建流、异步拨号和恢复仍可能继续。原子标记只发布不可逆意图及唤醒，不从调用线程修改 actor 的 stream／queue／cipher。关闭控制请求可用单独、容量为一的唤醒通道，由 actor 优先处理；重复请求不占用更多状态。

实现可选择以下一种 context 接线，必须在代码审查时固定一种完整方案：

- **推荐：保留 Session.ctx 为业务生命周期，增加同一父 context 派生的 control context。** 首个关闭決议立即取消业务 context 并同步清 DNS scope；actor、reader admission 和关闭控制使用仍存活的 control context，最终停止时也取消它。原来的 scope ctx 等于 owner.ctx 合同不变，票据／候选／attach 既有 ctx.Err 检查仍能拒绝关闭态。原子终态标记覆盖业务 context 取消前后以及 actor 尚未处理关闭请求的窗口。
- 若保持 Session.ctx 存活来承载控制，就必须另加独立业务 context，并让所有后台 guard、dial、Flow 和权限检查使用终态标记／业务 context。不能只在 Close 里加一个等待循环而把现有 ctx 检查都保留原样。

直接 abort，例如 Server 关闭、父 context 取消、设备撤销或寿命到期，应立即取消控制 context。它们不等待 Close 握手来延长权限或服务器停机。

`done` 继续表示 actor 及其登记资源最终收束；业务终态标记表示禁止继续使用会话。二者不能混用。特别是 Server maintenance 删除 UDP handle 的判断必须以控制 actor 已停止为依据。

## 4. 首次关闭时立即清理的资源

actor 开始关闭控制前，应执行幂等的业务清理，先完成清理才能 publication CloseAck：

1. 禁止新 OPEN、Dial、Write admission、class 更新和恢复激活；取消本端正在进行的恢复／建连候选。
2. 使 Session backend guard 立即失败，调用 once-protected scope cleanup，清空 DNS map 并取消 resolver scope。迟到 DNS 查询或数值拨号返回不得填充或交付。
3. 取消全部已登记 `st.dialCancel`；把各 Flow 标为失败并唤醒 OPEN、读写和写锁等待者；关闭全部已登记目标 socket，且底层 close 保持恰好一次。
4. 释放 chunks、segments、Flow 读缓冲、UDP messages／重组、classification 表、业务控制与恢复快照引用。清理总预算／统计，不通过队列发送新的业务信用、RESET、分类公告或 TicketRefresh。
5. 停止业务 scheduler 和普通 UDP retry loop；只留下固定数量的关闭状态、当前 carrier、必要认证／replay 状态和关闭控制 I/O。

不能直接复用会 enqueue 业务帧的 reset 后又继续运行普通 flush。现有 reset 在丢弃数据时可能 enqueue MaxSessionData；关闭清理需要无业务输出的终态路径或在清理后整体清空 scheduler，再由专门关闭控制分支负责发送。

`handleOpen` 的异步拨号结果提交点当前检查 `st.reset || s.ctx.Err()!=nil`。新实现还必须明确检查原子终态，确保即使 resolver／Backend 不遵守取消，迟到 conn 也只被关闭，绝不登记、bridge 或回送 ok。

已认证 Close 所在 record 剩余帧不能继续走业务 handle。收到合法 Close 后转入终态；同 record 中后续 OPEN、StreamData、ResumeState、TicketRefresh、ClassUpdate 等一律不产生业务副作用。必要的 canonical Close/Ack 可交给专用关闭处理器；不要为了处理后续普通帧又把业务 gate 打开。

内置 net／gateway 的 scope 和 socket 应提供可验证清理。任意不合作自定义 Backend、resolver 或 net.Conn.Close 可能无法在固定时间内结束 goroutine；实现必须限制其并发，永久拒绝迟到结果并保持配额到实际调用返回。不能把“权限与缓存已失效”写成“任意第三方执行任务都已结束”。已有统一 worker 退出边界尚待完善。

## 5. 原子终态 guard 的完整门禁

下一轮代码审查必须逐项核对，不能只测 Close 主函数：

| 门禁 | 关闭态要求 |
|---|---|
| Client.Connect 的当前 Session 复用 | 关闭请求后的旧 Session 不再可复用；Client 尚未关闭时另一次显式 Connect 可建立全新 Session，旧流不得迁移 |
| Client.recover 的取样、allowed、迟到 establish、attach 与 merge | 终态一旦发布就取消／拒绝旧 Session 候选；不得安装新 carrier 或续命 |
| Session.attachGuarded／activate／mergeInfo／sessionSnapshot | 拒绝关闭态，不允许重新变 active、synced，或导出可用于恢复的秘密 |
| Server.ticketValidLocked | live／overlap locator 都立即失去恢复资格；不能等待每秒 maintenance |
| Server.candidateValidLocked、initialize 缓存及 committed confirm/READY | 对关闭态 Session 返回失败；即使 cached INIT／READY、候选已认证或本轮 generation 已提交也不能绕过 |
| Server.rotateTicket 和 late refresh | 不注册新 locator，不使删除后的 alias 重新出现 |
| Session backend guard、DNS query／cache-hit／late fill、dial 提交 | 终态在调用前、结果提交前均被检查；cleanup 恰好一次 |
| DialMetadata、Flow.Write 的 admission commit、Datagram batch | 不消耗新流号、分类／缓冲／message id，也不提交排队业务 |
| 接收 OPEN、恢复快照、业务、分类与 ticket | 不分配新状态或目标；旧帧不复活 Flow／Session |
| bridge 完成回调和旧 commands | 只收束／释放，不恢复状态或 enqueue 新业务 |
| Server UDP router 与 handle maintenance | drain 内保留当前有效 handle；拒绝旧 carrier、旧地址、未认证输入；停止后删除 handle |

已有 atomic revoked、不可变 lifetime 和父 context 检查继续存在。终态 guard 不能取代权限撤销、寿命或源地址绑定。

## 6. Close、ACK 和重复消息的控制流程

本端主动关闭固定一次 `localCloseRequested`。可用专门的单槽 close operation，不需要塞入可能已经耗尽的普通 8192 项 operation 表。若复用 operation 表，则必须为 Close 保留独立容量、修改 request／ACK 映射、调度与耗尽路径，并证明普通表满不会阻塞终态控制；只增加一个 key 映射不完整。

发送端仅在完整认证 record 实际写入成功后记录本端 Close publication。收到当前 carrier 上的 canonical CloseAck 时，只有 `localCloseRequested && successfullyPublished` 才能报告远端确认。未请求／未 publication 的 ACK 不完成本端关闭，不触发新的关闭请求；建议忽略无关联 ACK。失败／短写、预算未准入和 enqueue 不算 publication，ACK 等待不以它们为成功起点。

接收端首次收到 canonical Close，立即进入业务终态并完成资源清理，然后发送 ACK。它保留一个固定、不延长的回应期限，以便收到新 record number 携带的重复 Close 时重发 ACK。重复 Close 不重做 DNS cleanup、不再次 Close 目标、不拨号、不刷新 deadline、不分配多个回应条目。相同 ciphertext 的网络重放仍按 record replay 规则处理；不得放宽认证 replay 为关闭保活。

双方同时主动关闭时，分别维护“本端 Close 已 publication／获 ACK”和“收到对端 Close／需 ACK”。收到对端 Close 不等于本端 Close 获得确认；本端获 ACK 也不能忘记尚处固定回应期的对端 Close。若采取提前结束，必须明确说明对端丢失 ACK 时会走未确认结果；推荐对已收到对端 Close 的 actor 留到原有固定 drain deadline，以处理其重复通知。

关闭期间禁止普通 Ping、rekey、ticket、snapshot、class、StreamData 和 Datagram 自动重试；这些不能刷新关闭期限。PacketAck、Pong 和其他认证帧不满足 Close 逻辑完成条件。也不再因为关闭状态的 transport stall 自动恢复同一 Session。

## 7. 期限与发送资源预算建议

以下是**下一轮待代码审查的默认选择**，尚未实现或测量，不改写现有生产 15 秒 UDP watchdog、30 秒 RetainTimeout 或原 8 秒业务操作期限：

| 项目 | 建议 | 选择理由 |
|---|---|---|
| Close 控制总期限 | 新增明确的 CloseTimeout，默认 3 秒；第一次请求或第一次合法 peer Close 时固定 | 独立于业务、恢复和保留期；允许低吞吐链路上有限往返，又不令 API 为普通关闭等待 30 秒 |
| 有效绝对截止 | `min(closeStart+CloseTimeout, 固定 Session lifetime, 已存在的 suspendedAt+RetainTimeout)` | 关闭不能延长已有资格、旧保留期限；后续请求、ACK、帧和 attach 不重置 |
| 请求 publication | 最多首次加 4 次，共 5 次 | 一次业务终态只有一个逻辑请求；通知丢失时可补发，且限制总体网络负担 |
| 请求重试间隔 | 200、400、800、1000 毫秒封顶；默认无阻塞时约在 0、0.2、0.6、1.4、2.4 秒 | 给 ACK 留出观察期；实际写成功才消耗一次 publication，不能因为每个 actor tick 又发送 |
| 回应 publication | 最多 8 次；重复 Close 的回应最短间隔 200 毫秒，合并 pending | 足以覆盖常规有限重试；认证重复洪泛不能生成无界回应或记录 |
| 发送槽与字节 | 固定一个请求槽、一个回应槽；最大 5+8 份 record | 不依赖普通 queue/table 空间，memory 与对端消息量脱钩 |
| padding | 优先沿用现有 LIGHT、MaxOverhead=256 | 保留已有混淆包络分布；不要借实现关闭取消随机填充 |
| 单份 Close record 界 | `28+256+48=332 B` 的保守上界，不含 IP/UDP/TCP 头和 TCP framing | 由现有 HeaderSize、padding 上界和 RecordOverhead 导出，不以 plaintext 长度当线上成本 |
| 每 Session 控制字节界 | 至多 `13×332=4316 B` 的认证 record，固定生命周期内累计；无自动补充预算 | 完全脱离业务 cwnd/pacer 后必须有可审计的独立小预算；旧业务预算不能被关闭 control 成功“补满” |
| TCP 单次 write | 使用现有 2 秒上界与关闭绝对剩余时间的较小者 | 原 carrier.write 的“每次重新给 2 秒”会使最后一次发送越过总关闭截止，须显式 clamp |

普通关闭队列不能绕过饱和 cwnd／pacer。建议终态后使用专门 Close/Ack 发送分支，直接使用当前 cipher 和 carrier，按上述累计份数／字节和 deadline 控制；它不是普通反馈 reserve 的无限入口。不修改旧 flight／cwnd 数值来虚造空余预算，不触发普通 loss/PTO，也不借封包成功把业务统计写成交付成功。旧 ledger 和业务引用应在终态清理中释放或按固定元数据边界收束，不因 ledger 的 MaxLivePackets 饱和阻断 Close；控制 publication 单独记录。

该分支无业务同步门槛：已经完整握手认证的 carrier 即使 ResumeDone 尚未完成，也可发送终态 Close/Ack。没有可用认证 carrier 或已有 carrier 错误时只能本地清理并报告未确认，不能靠未认证 bootstrap 来宣告关闭。

actor 不应在关闭请求后继续普通四帧 flush，避免 TCP 最坏四次 2 秒写入把开始关闭拖至 8 秒。正在进行的一次 socket write 仍受已有 deadline 约束；结束后检查终态并立即切换关闭分支。对可并发使用的真实 TCP socket，可用期限收紧解除旧写入阻塞；不能给 Server 共用 UDP socket 设置某个 Session 专属写截止，影响其他 Session。

若实现需要全局 responder 限额，应由 Server 持有，且不得把 closing Session 从 MaxSessions 计数立即移除再无限创建 drain tombstone。现有默认 MaxSessions=64；每项固定状态、固定期限和总 publication 预算可给出上界。是否拆分 active／closing 配额，应单独说明拒绝行为并测试。

## 8. API 结果、远端黑洞与诚实边界

CloseAck 的含义应是“对端已作出不可逆终态决定并清理其登记业务资源”，不是“对端控制 actor／router tombstone 已消失”。对端仍可在固定期限内保留认证回应能力。

建议 `Session.Close() error` 同时完成本地清理并等待有界控制结果：确认时 nil；deadline、无 carrier 或写错误时返回稳定的未确认关闭错误。本地终态与清理无论结果都成立。可以用专门错误及有限 reason enum 区分 deadline／carrier；不要暴露目标、票据或原始敏感错误。Client.Close 需传播该结果，不再无条件丢弃。

相同对象的重复／并发 Close 应共享首次决议、首次 deadline 和最终结果。第二个调用不能在首个关闭仍进行时因 CompareAndSwap 失败立即返回 nil；这是完成语义问题，而非仅“没有重复发送”。需要 once／completion channel／immutable result。若保持当前 Close 返回仅表示本地释放的 API 合同，应另提供明确的关闭确认接口或诊断，不能用 nil 宣称对端已确认。

必须分别验证两类失败：

- **通知到达、CloseAck 全丢。** 接收端 DNS 和目标立即清理，保持有限 ACK 回应；发送端有限重试后返回未确认并本地释放。它不是远端资源泄漏，也不能把发送端未确认偷偷记为 ACK PASS。
- **所有 Close 与 ACK 被完全黑洞。** 对端没有获知终止意图，有限重试不能保证它在本端 3 秒截止内立即清理。本端停止业务与回应后，对端沿原有路径进展检测进入暂停，再在固定 RetainTimeout 清理。必须实测并记录最后有效 transport progress、首个未确认 ack-eliciting 发送、watchdog 暂停时刻、固定 retain 起点及清理时刻；不能仅以本端 Close 返回证明远端清空。

默认 15 秒 watchdog 加 30 秒 retain 是不同阶段，不是总计 30 秒或“3 秒关闭保证”。在已拥有未确认 UDP record 的常见静默场景，远端收束预算由其原路径进展截止加固定保留期决定，actor／socket 调度还有明确观察余量；若当时无在途 record，下一份正常探针启动检测之前还存在 ProbeInterval。应从对应原始状态推导总界并实测，不能把 45 秒理论和当次实测混为同一结果。

完全丢包的分布式系统无法从本端动作推断对端已经收到关闭。若产品要求远端在更短固定期限内必然销毁，必须设计显式 Session 租约／独立业务保活合同并协商，不能缩短既有 watchdog／retain 或用修改测试期限假装关闭协议实现了这个要求。

## 10. 实施边界与完成条件

下一轮完成的最低条件是：上表实际实现门禁齐全；原子终态、立即资源清理和有限控制 actor 的语义一致；通知／ACK 丢失、预算饱和、同 record OPEN、恢复竞争、late DNS／socket、完全黑洞和 registry 收束均有对应证据；错误、publication 与资源预算没有被日志或测试隐藏；全文中待实现的默认预算已与最终源码核对。

该阶段通过也不等于 BFP 全部验收。默认 8 秒内稳定 UDP→TCP 恢复、分类 WAN 收敛、公平性、可靠性／纠错策略、TUN／fake-IP／客户端 DNS／IPv6 适配和独立安全审查仍需按原目标继续完成。不得因此将 `acceptance_complete`、`production_ready` 或 `released` 改为 true。
