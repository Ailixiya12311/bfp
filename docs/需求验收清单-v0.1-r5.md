# BFP 需求验收清单 v0.1-r5

日期：2026-10-07。依据：[协议技术设计 v0.1](协议技术设计-v0.1.md)、冻结的 r5 Go 源码及本轮验证记录。用途是把原需求逐项对应到实现和证据，作为继续开发与最终验收的清单。r5 本地测试和竞态测试通过，**双机 WAN 严格 FAIL**；当前没有 R1–R9 或技术设计全部完成的结论。

本文使用 r5 本地验证、冻结源码 Linux 竞态和新 ELF 双机 WAN 的独立记录，不得用 r3 双机结果代替 r5。源码位置按 r5 快照标注；后续修订须独立关联源码、构建摘要与验证证据，r5 的通过或失败不能自动转移到 r6。

状态用语：**已落地并有本地证据**表示明确的实现行为已在本轮用例中验证；**部分落地**表示需求还有代码或覆盖缺口；**待实测**表示代码存在但对应真实条件没有当前证据；**待实现**表示尚无接入代码或所需机制；**可选扩展**与**范围外**分别沿用原设计的可选项和排除项。本文不计算“完成百分比”，也不将测试事件数等同于需求项数。

### 2.1 r5 WAN 失败与可确认事实

新加坡发送、洛杉矶接收/出口，使用本次 r5 ELF。生命周期参数 TTL 12s、提前 8s、旧 alias 6s、最大寿命 5min；探针间隔 250ms，每场 50 次 TCP 16KiB 往返与 50 次 UDP 业务往返。实际业务时间均超过原 12s TTL，三场都观察到客户端安装刷新，但这不消除业务失败。

| 场景 | TCP / UDP 成功 | 承载与原连接 | 业务耗时 / 客户端刷新数 | 原始场结果 |
|---|---|---|---|---|
| 正常 UDP | 50/50；50/50，UDP failed=0 | UDP gen1；同 Session，唯一原目标 TCP socket | 55.389s / 14 | [normal_udp.evidence.json](../lab/runs/0387f1ac577e411ad6b1d3edbb4e643c/normal_udp.evidence.json) `pass=true` |
| 运行中 UDP 黑洞 | 50/50；24/50，UDP failed=26 | UDP gen1→TCP gen2；同 Session，唯一原目标 TCP socket | 39.268s / 8 | [udp_to_tcp.evidence.json](../lab/runs/0387f1ac577e411ad6b1d3edbb4e643c/udp_to_tcp.evidence.json) `pass=false` |
| 启动前 UDP 黑洞 | 50/50；20/50，UDP failed=30 | TCP gen1；同 Session，唯一原目标 TCP socket | 35.979s / 9 | [initial_udp_blocked.evidence.json](../lab/runs/0387f1ac577e411ad6b1d3edbb4e643c/initial_udp_blocked.evidence.json) `pass=false` |

UDP→TCP 场的 [probe-log.json](../lab/runs/0387f1ac577e411ad6b1d3edbb4e643c/udp_to_tcp.probe-log.json) 显示第 24 次请求在稳定 TCP gen2 上达到 1s 截止，第 25 次起多次是立即返回的非 timeout 失败。r5 probe 发送后只读一次并比较 payload，前次迟到 UDP 回声可能使后续比较串位。因此这 26 个失败不能直接等同于 26 个协议丢包，也不能假定全部是探针问题后改为通过。初次截止仍是实际请求失败；须修复探针相关性、保持原 1s 截止和严格成功标准，在新修订中复验。

正常/切换/初始 TCP 三场最大 TCP 操作时长分别为 2168/4249/1864ms，包含整次 write/read 操作，不是纯切换暂停。它们不构成 goodput、尾延迟或调度公平性报告。

同 run 未授权探测为 16 UDP、8 TCP，无应用回复且 target-open 3→3；owned 进程和目录清理完成。洛杉矶原严格快照门禁另因已有 Xray 动态 UDP socket 变化失败，[supplemental-baseline-review.json](../lab/runs/0387f1ac577e411ad6b1d3edbb4e643c/supplemental-baseline-review.json) 确认既有服务固定端点/容器/路由/防火墙稳定，但 `code_checks_pass=false`：**宿主补充核验通过不能覆盖两个业务场失败，整个 r5 WAN 保持 FAIL**。

| 探测 | 无效 UDP/TCP、raw slot 与期限回归 | 慢首包、重放/未知句柄/版本、高频压力与开销边界。 |
| 抗放大 | 实际 Noise/CONFIRM/READY 预算、来源绑定 | 伪造源/变源/跨候选/重试累计响应的完整压力矩阵。 |
| 密钥 | 双向真实重键与旧 epoch 退役、边界单测 | 完整向量、高速更新/重排/跨承载/计数器组合与审查。 |
| 接入 | 本项目 SOCKS 的局部用例 | 两款真实软件 SOCKS/TUN 与 native 各自构建/完整支持矩阵。 |

## 8. 可选项与明确范围外

| 项目 | 原设计范围 | 处理方式 |
|---|---|---|
| FEC | 可选扩展，首个 PoC 关闭，TCP 初版关闭额外 FEC | 不作为本轮完成门禁；若后续启用，再冻结认证顺序、符号/内存/冗余预算并做对照。 |

## 9. 达到原目标的最小连续实现顺序

1. **保留 r5 失败并修复验证相关性。** local/race/fuzz 已有独立证据；r5 WAN 三场结果与宿主核验分别保留。修复 UDP probe 只读一次引起的迟到消息错配，以新修订独立构建/验证，保持 1s 截止与严格失败统计；复验三场、跨 TTL 刷新与原目标 socket 连续性。不得覆盖 r5 FAIL、延长截止掩盖初次失败或沿用 r5 race 推导新修订通过。
2. **把分类组件接入实际会话。** 接入可信元数据、服务端 cap、新增唯一业务字节/tick、迟滞；冻结 ClassUpdate 的版本/确认/恢复状态，接入 `ReclassifyFlow` 与每类/每流限制。沿用 TCP/UDP 交付语义和 OPEN 不可变目标，增加真实 Session 混合负载验证。
3. **完成传输与可靠控制合同。** 将采用的 ACK 范围/delay、RTT/PTO、健康检测、拥塞/pacer 和最新逻辑控制恢复方案独立冻结与验证；补最后 ACK/信用丢失、OPEN 拨号中切换、候选失败等原矩阵。算法候选若调整需同步技术设计，以实际丢包/高 RTT/背压和同方向混合流实验验收。
4. **补齐资源与销毁验收。** 来源级/每设备/全局目标和字节预算、有限控制机会、所有异步任务退出与引用清理；在重复建销、慢目标、坏首包和持续混合负载下记录 CPU/RSS/socket/内核资源及部署配置。与第 3 步独立的预算/清理工作可并行。
5. **冻结协议协商与安全规范。** 认证版本/能力/LIGHT 上限、未知字段和拒绝策略；形成握手、准入、恢复、record、KDF/头保护/TCP 长度保护的确定性向量，开展持续 fuzz、互操作和独立专项评审。实验中的自定义密码封装不能靠单元测试直接变成生产安全结论。
6. **交付真实接入与最终完整矩阵。** 先对已实现 SOCKS 路径运行固定版本 Mihomo/sing-box 的 TCP/UDP/DNS/IPv6/fake-IP/TUN/路由排除；再按原目标实现两款 native outbound、配置与构建，并分别验收。完成真实 goodput/尾延迟、故障与长时稳定性，逐组关闭第 7 节的剩余项。

以上顺序沿用原设计 P0–P5 的目标，没有把 FEC、SHAPED/COVERED、自动 UDP 回切、mesh 或新增管理面变成强制要求。当前可交付结论是**核心两端协议和凭证生命周期有 r5 本地/竞态证据，分层调度已接入；分类器接线、完整传输合同、系统预算、协议冻结/审查和真实接入仍须连续推进**。
