## 1. 本轮冻结修订与证明目标

本轮范围为 UDP probe 阶段遥测、Session UDP 写入的固定 deadline 准入，以及 TCP carrier 输入背压。新 probe 遥测将 API 写入、读取、Session Stats 等阶段分开记录，以便定位后续实网失败；它不增加业务重传、不续期 1s 截止、不覆盖首次失败。Transport 修复针对受控 fixture 已复现的两项行为：actor 被 TCP 写入阻塞时，超时 UDP 准入仍晚提交；TCP incoming 队列满时，已读出的完整记录被静默丢弃。

## 2. Probe 遥测合同与时间边界

调用方在第一份同步 `Stats()` 之前记录 `udpStarted`，UDP 操作截止仍为 `udpStarted + 1s`，如 probe 整体 context 更早到期，则取更早时间。`Stats()` 消耗的时间属于这 1s 预算；helper 只设置一次绝对 deadline，每个业务消息最多 Write 一次。迭代失败仍立即计入 `udp_failed`，最终门槛仍为 `udp_ok == count && udp_failed == 0`。

| 字段 | 本轮定义与解释限制 |
|---|---|
| `write_attempted` | helper 即将调用一次 `net.Conn.Write` 时置 true；写入前已过期则为 false |
| `write_accepted` | 只表示这次 `Write` 完整返回，即 `n == len(message)` 且 `err == nil`；不证明 Session 已入队、线上已发送或目标已执行 |
| `write_elapsed_ms` | 单次 Write 调用经过的时间；不是目标处理时间 |
| `read_elapsed_ms` | 读取阶段经过的时间，包含缓冲分配、deadline 检查、回包关联和 Read 调用；不是纯阻塞 Read 时长或 RTT。`before_read` 可有很小非零值 |
| `stats_before_ms` / `stats_after_ms` | 两次同步 Session Stats 的经过时间；Stats 本身不保证以 UDP deadline 取消 |
| `exchange_elapsed_ms` | 整个 helper 的经过时间；总体 UDP elapsed 还包含 Stats 与周边工作 |
| 毫秒加总 | 各阶段独立向下取整，因此分段毫秒之和不要求等于总体 elapsed |
| 回包关联 | 只输出有界规范 iteration、计数与固定错误类型；无关/迟到回包在原截止内跳过，不写入原始内容或秘密 |

| `error_phase` | 发生位置 |
|---|---|
| `set_deadline` | SetDeadline 失败 |
| `before_write` | 调用 Write 之前已到原截止；没有写入尝试 |
| `write` | Write 出错或短写 |
| `before_read` | Write 完整返回后，第一次 Read 之前已到原截止；没有 Read 调用 |
| `read` | 已进入读取/关联阶段，包括连续无关回包耗尽原截止 |
| 空值 | helper 成功匹配完整当前消息 |

新增读取计时使用 named return 和 deferred 赋值，以保留错误返回的阶段时长。已有迟到/重排、重复/短报、连续错误回包不续期、关闭/普通 I/O、缓冲旧报和有界编号测试继续执行；新增写入前到期无副作用、慢 Write 消耗原预算后不读取缓存正确回包的场景。上述 6 个 probe 顶层测试已在第 6 节正式全包验证中执行并通过。

## 4. 固定 UDP 写入 deadline 的当前合同

UDP `Flow.Write` 在取得 `writeMu` 后读取当前 `writeDeadline`，以固定快照建立 `context.WithDeadline` 并使用既有 `Session.call`。actor 闭包入口和消息编号/分片提交之前再次检查 context 与墙钟；取消赢在提交之前时，返回带 `net.Error.Timeout()` 的 write 错误，不消耗 messageNext，不留下取消请求的碎片。messageNext 到 `uint64` 最大值时先拒绝，避免环绕。

既有 call 机制区分尚未开始与已开始的命令：超时可取消未开始的命令；若提交检查已经通过并进入有限 actor mutation，则等待它完成并返回实际结果。因此本轮不声明“所有 Write 在 deadline 那一纳秒必然返回”，也不把完成 mutation 后的实际接受结果伪装成没有发生的超时拒绝。

整 datagram 先按 `payload + parts × (HeaderSize + 48 + 256)` 检查当前 Session 队列总字节余量。当前 Session 初始化/重建均使用总字节预算构造器，单片实际费用不超过该保守估算，且 actor mutation 没有其他入队交错；对应边界下全报预算检查覆盖各片 Push。将来接入更紧的每类/每流/项数限额时，必须加入整报 reservation/事务合同，不能沿用本轮推论宣布不会部分入队。

仍存在以下边界，后续要独立实现与验证：

- Write 期间并发 `SetWriteDeadline` 更改不会重设该次 UDP context；本轮只覆盖调用时取得的固定快照，未实现完整 net.Conn 动态 deadline 合同。
- 同一 Flow 多个 Write 在 `writeMu` 上的锁等待没有 deadline 退出通道；deadline 在取得锁后才读取，故本轮 fixture 不证明并发锁等待也按截止返回。
- Session 未 active 或 peerDone 未完成时，UDP 仍保留现有 best-effort 丢弃并返回完整 API 写入的行为；`write_accepted` 不能用来证明队列准入。
- helper 的前后时间检查能阻止超期后把缓存回包计为成功，不能使任意不响应 deadline 的连接实现自行停止阻塞。

## 5. TCP 输入背压与退出边界

TCP 已读出的完整 carrier record 或 read error 改为等待进入有界 incoming 队列。等待不持有 actor、Flow 或 Server 锁；incoming 满时 reader 不开始下一次 socket Read。Session context 取消、Session done 或该 carrier 的 closed signal 都能退出入队等待。carrier.close 先关闭 signal 再关闭 socket，因此旧 generation 的 reader 不必等待 actor 再处理命令才能退场。UDP 满 incoming 继续非阻塞丢弃，避免一个 Session 阻塞共享 UDP 收包循环。

这项背压使 TCP 完整记录不再因本地入队满而静默丢失，但没有将 actor 的网络写入移出 owner 循环。两端都因 incoming 满而停读、同时 actor 正在写入时，可能形成双向 socket 压力。现有 TCP carrier 每次 Framer.Write 仍设置 **2s 写 deadline**；写入失败可触发 suspend 并关闭 carrier，因此不能据本轮满队列 fixture 宣布无暂停、无 head-of-line 延迟或长期双向压力永不触发重连。真实负载下的暂停、超时和恢复需另行测量。

因此新增遥测将本次失败定位到读取等待，而本轮固定 deadline 准入和 TCP 输入背压的受控修复仍有对应本地证据；这些结果没有消除实网首个 UDP 失败，也不能据此证明两个 Transport 缺陷就是 r6 首次延迟的根因。整个 WAN 和候选仍严格 FAIL，不发布 ZIP。

同 run 16 UDP、8 TCP 未授权样本应用响应均为 0；部分 TCP 为超时、部分为 reset，不能把“无应用响应”写成“没有任何网络响应”。目标连接累计数 3→3，无新增出口副作用。洛杉矶 2 个、新加坡 6 个 owned 进程全部停止，两机 run 临时目录及其中秘密已删除，原始清理保存于 wan-result。
